# Проєктування інсталятора

<!-- SPDX-License-Identifier: LicenseRef-Volnist -->

> **Обов'язкова продуктова вимога власника (2026-11-28): WSM має надати користувачеві вибір між трьома способами встановлення.** Це не взаємовиключні альтернативи й не послідовне відкладання GUI:
> 1. **Консольний CLI** — звичайний текстовий покроковий інсталятор без повноекранної псевдографіки.
> 2. **Псевдографічний TUI** — повноекранний термінальний інтерфейс із рамками, навігацією клавішами та українською локалізацією.
> 3. **Графічний Calamares** — повноцінний графічний майстер, який користувач може вибрати окремо.
>
> Основний універсальний інсталяційний Live-образ має містити всі три режими та показувати видимий WSM Installer Selector. Мінімальний CLI/TUI-образ може залишатися додатковою редакцією для слабкого обладнання, але не замінює універсальний образ і не може рекламуватися як такий, що має всі три режими, якщо Calamares у ньому відсутній.

## Контракт трьох frontend-ів

| Режим | Користувацький досвід | Обов'язкова роль |
| --- | --- | --- |
| **Консольний CLI** | Звичайні текстові prompt-и, повідомлення та підтвердження; без ANSI-повноекранного UI | Доступний для serial/headless та мінімальних середовищ |
| **Псевдографічний TUI** | Повноекранні термінальні екрани, рамки, стрілки та клавіатурні скорочення | Доступний без desktop/Qt і без GPU |
| **Графічний Calamares** | Графічний wizard: мова, клавіатура, профіль, розмітка, підсумок, підтвердження й перебіг інсталяції | Обов'язковий GUI-шлях, а не reference-only чи майбутня необов'язкова ідея |

Ці три способи мають бути **видимим вибором користувача** в основному інсталяційному Live-сеансі. Після завантаження запускається WSM Installer Selector з трьома пунктами. Він може бути графічним launcher-ом у desktop-сеансі та еквівалентним консольним меню для текстового запуску. Вибір одного режиму не повинен автоматично підмінятися іншим; у разі відсутності потрібного компонента слід показати чітке пояснення.

wsm-install у консольному режимі й wsm-install --tui (або еквівалентний окремий entrypoint) є **двома самостійними frontend-ами**. Консольний CLI не можна зводити до псевдографічного TUI, а Calamares не можна замінювати desktop-shortcut-ом, який запускає TUI.

## Єдиний planning і deployment contract

Усі три frontend-и використовують однакову послідовність:

1. Локальний wsm-hwcheck збирає hardware evidence; звіт не надсилається в мережу.
2. Користувач обирає один із трьох frontend-ів.
3. Обраний frontend показує hardware evidence, дозволяє вибрати профіль і формує типізований draft plan.
4. Користувач перевіряє цільовий диск, розділи, firmware mode та підсумок, після чого дає окреме явне підтвердження.
5. Єдиний WSM Guix backend перевіряє plan/target і виконує deployment.
6. Після встановлення перевіряється результат та створюється зрозумілий звіт.

Frontend відповідає за подання й взаємодію; він не стає другим системним backend-ом. Calamares може надавати власний UX і partitioning view, але deployment, Guix-конфігурація та встановлення bootloader мають залишатися узгодженими з єдиним WSM/Guix ownership contract. Заборонено запускати два writers для partitioning, root filesystem, bootloader або system activation.

## Поточний стан реалізації (не плутати з цільовою вимогою)

| Компонент | Що існує | Що ще не доведено |
| --- | --- | --- |
| Консольний CLI | wsm-install та guided text path для preflight/plan | Повний покроковий destructive installation flow |
| Псевдографічний TUI | wsm_install/tui.py, wsm-install-live, unit tests | Повний інтерактивний шлях на реальному ISO в BIOS та UEFI |
| Calamares | Заготовка WSM Python jobmodule та дослідницькі ADR | Guix package/closure, settings.conf, повний module chain, запуск у live ISO та реальне встановлення |
| Installer Selector | Поки не реалізований як єдиний вибір трьох режимів | Меню, яке перевіряє доступність компонентів і запускає кожний режим |
| Спільний APPLY | Typed plan/handoff та preview-only adapter-и | Безпечний reviewed apply + disposable-disk installation/boot acceptance |

У поточних RC APPLY вимкнено. Наявність CLI, TUI, Python-файлу Calamares або BIOS/UEFI boot marker не означає, що система вже встановлюється. Зокрема, опублікований RC6 Minimal Live — це preview без Calamares і без повноцінного APPLY; він не відповідає цільовому all-in-one UX із трьома варіантами.

## Образи та доступність режимів

| Образ | Режими | Призначення |
| --- | --- | --- |
| Основний універсальний Live Installer | **CLI + TUI + Calamares** | Головний рекомендований образ; містить selector і всі три frontend-и |
| Додатковий Minimal Live | CLI + TUI | Резервний шлях для дуже слабких машин, serial/headless та відновлення; не замінює універсальний образ |

Наявність KDE/Qt/Calamares у головному образі — усвідомлений компроміс заради повного вибору. Мінімальна редакція потрібна додатково, а не замість графічного інсталятора.

## Критерії готовності трьох режимів

- Selector реально показує всі три режими в основному ISO й кожен пункт запускає саме заявлений frontend.
- Консольний CLI проходить свій сценарій без ANSI TUI; TUI перевіряється як окремий повноекранний сценарій.
- Calamares збирається з pinned upstream source та повним partition module/KPMcore; його settings і WSM jobmodules проходять runtime acceptance.
- Усі режими споживають той самий hardware report та typed plan schema.
- Кожний режим має однакове явне підтвердження цілі та передає роботу тільки одному Guix backend-у.
- QEMU acceptance перевіряє всі три user journeys, фактичне встановлення на disposable qcow2, BIOS/UEFI та повторне завантаження встановленої системи.
- Окремо тестується відсутність Calamares у Minimal Live: selector не показує фальшивий доступний GUI пункт, а повідомляє про обмеження цієї редакції.

## Історичний дизайн і технічні нотатки

Решта цього документа містить деталі інтеграції Calamares і Guix. Вони описують технічну реалізацію цільового графічного frontend-а; історичні позначки proposed в ADR не скасовують наведену вище продуктову вимогу власника. ADR та issue #10 мають бути узгоджені з нею окремо.


## Модульна модель Calamares

Calamares розрізняє user-visible view modules та job modules. View modules реалізуються як Qt plugin (C++/QML); Python interface призначений для job modules. Python job module має module.desc із назвою скрипта (зазвичай main.py) та функцію run(). Успіх повертає None, помилка — пару рядків із повідомленням і деталями.

Перед реалізацією адаптера потрібно зафіксувати конкретну версію Calamares і перевірити її inline Python API. Не слід програмувати проти випадково знайденого прикладу іншої версії.

## Цільовий workflow графічного Calamares (ще не реалізовано)

Наведений workflow є цільовою специфікацією графічного шляху. Він ще не реалізований і не повинен видаватися за доступну можливість до завершення package, settings, module та QEMU acceptance.

1. Welcome та інформація про статус підтримки й доступні режими інсталяції.
2. Мова, клавіатура та часовий пояс.
3. WSM hardware preflight: локальний звіт, статуси пристроїв і попередження.
4. Пояснення readiness та вибір профілю Free або Compatibility.
5. Вибір цільового диска й розмітка через Calamares/KPMcore; до явного підтвердження — лише формування плану.
6. WSM configuration summary: диск, partition plan, mount points, profile, firmware/boot mode.
7. Перевірка свіжості hardware evidence та повторна перевірка identity цільового диска.
8. Явне підтвердження незворотних дій із точним показом, що буде стерто/створено.
9. Передача типізованого plan єдиному WSM Guix backend; backend повторно перевіряє ціль.
10. Guix system build / перевірка конфігурації та deployment через один owner.
11. Post-install verification, включно з файловою системою та bootloader.
12. Перевірка завершення, звіт і зрозумілий стан успіху/помилки.

## Що не можна просто взяти зі стандартного Calamares

### Bootloader

Guix configuration має бути єдиним джерелом істини для bootloader. Стандартний Calamares bootloader job не повинен запускатися паралельно, якщо Guix system init встановлює завантажувач сам.

### Users

Стандартний users module не вважається сумісним із Guix System автоматично. Guix user accounts є частиною operating-system declaration. WSM має сформувати декларацію користувачів, обробити пароль через перевірений механізм і не зберігати його у відкритому вигляді.

### Filesystems

План mount points, файлових систем, UUID/labels та EFI System Partition має бути пов'язаний із згенерованою Guix-конфігурацією. Не можна будувати конфігурацію з неперевірених рядків.

## Межі WSM deployment adapter

Рекомендована перша форма — Python job module Calamares, якщо її API та потрібні права доступу підтверджені для вибраної версії. Модуль повинен:
- читати лише визначені ключі з Calamares global storage;
- перевіряти, що target root і EFI mount points очікувані;
- відмовлятися працювати з неоднозначним або неповним partition plan;
- генерувати конфігурацію із типізованих даних;
- запускати Guix через офіційний API команд Calamares, а не через shell string concatenation;
- повертати структуровану помилку в разі невдачі;
- не записувати секрети в логи.

Використання os.system(), shell=True або довільної shell-команди, складеної з тексту інтерфейсу, заборонене.

## Обов'язкові можливості збірки

Для WSM prototype потрібні Qt 6, Python job modules API та справжній Calamares `partition` module із KPMcore. Збірка, у якій KPMcore відсутній і partition module пропущений, не проходить критерії WSM, навіть якщо основний executable зібрався.

Потрібно перевірити Qt6 Polkit integration та runtime paths у Guix. Не вимикайте INSTALL_POLKIT для кінцевого образу без окремої перевіреної політики привілеїв і security review.

## Поточний стан

Calamares є обов'язковим графічним frontend-ом основного універсального WSM Installer Live ISO, але його реалізація ще не готова. У репозиторії є заготовка WSM Python jobmodule; немає підтвердженого Guix package/closure, повного settings.conf, повного module chain, запуску в live ISO або реального installation acceptance. Перелік конкретних частин і критеріїв — у README installer/calamares/. Поточний RC6 Minimal Live не містить Calamares і не є доказом готовності графічного шляху.
