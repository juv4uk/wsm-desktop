# Політика Git-тегів WSM

<!-- SPDX-License-Identifier: LicenseRef-Volnist -->

Статус: чинна технічна політика для нових тегів і безпечного впорядкування історії.

## Для чого існують різні простори тегів

Тег має називати **версію продукту або конкретний незмінний знімок**. Ідентифікатор запуску CI не є версією продукту.

| Формат | Призначення | Правило |
| --- | --- | --- |
| `0.1.0-rcN-minimal-live` | Кандидат WSM Desktop Minimal Live | Один тег на один source commit і один RC |
| `wsm-tools-<version>` | Версія архіву WSM/Guix tools | Без SHA та номера запуску в імені; вони належать provenance |
| `h170-free-pack-<sha12>` | Незмінний знімок H170 Free package manifest | Короткий SHA є ідентифікатором саме цього знімка |
| `h170-free-cache-<run-id>-attempt-<attempt>` | Окремий знімок substitute cache | Технічний тег запуску, не версія WSM |
| `h170-gp107-linux-libre-<version>-<sha12>` | Збірка пакета Linux-libre для конкретного source commit | Версія пакета разом із SHA джерела |

Номери запусків, повторні спроби, SHA джерела, Guix lock commit і контрольні суми зберігаються в `PROVENANCE.txt`, маніфестах та GitHub Actions run metadata. Їх не треба дублювати в імені звичайного версійного тега.

## Правила створення

1. Не створювати Git-теги лише для запуску workflow. Для ручного запуску використовувати `workflow_dispatch`.
2. Не створювати новий тег на кожну повторну спробу CI. Якщо source commit змінився після невдалого кандидата, призначити наступний RC; якщо source той самий, повторно перевірити той самий draft.
3. Опубліковані теги не пересувати й не перевикористовувати. Нові байти мають отримати нову версію.
4. Відкликані збірки залишати як історичні записи з явним `WITHDRAWN` у назві Release. Їхні теги не є шаблоном для наступних релізів.
5. Release без відповідного Git ref — помилка цілісності. Перед публікацією перевіряти, що `refs/tags/<tag_name>` існує і вказує на source commit у provenance.

## Поточна історія репозиторію

### Залишити незмінними

- `0.1.0-rc1`, `0.1.0-rc2-live-iso`, `0.1.0-rc3` і `0.1.0-rc6-minimal-live` — історичні точки релізів WSM Desktop.
- `h170-free-pack-469e4f93a199` — опублікований H170 Free package snapshot.
- `wsm-tools-*-run-*` та `wsm-channel-*` — відкликані спроби публікації з власними source commit і run ID. Їх збережено як provenance/audit trail; повторно такі імена не створювати.

### Відновити

У GitHub Releases є три чернетки Minimal Live, але їхні відповідні Git refs відсутні. Відновлюємо refs лише за точними commit SHA, які вказані в самих Release:

| Тег | Source commit |
| --- | --- |
| `0.1.0-rc3-minimal-live` | `fb5d27a7aa0b156183fdee842acb06da9dcb64ca` |
| `0.1.0-rc4-minimal-live` | `e042fba5fd1faad5ccb2fb432183a80f4e0286ad` |
| `0.1.0-rc5-minimal-live` | `873cf9660a686f9ae28cf41045344aaab02b4b52` |

Це відновлення відсутніх refs, а не пересування чи переписування комітів.

### Видалити як застарілі CI-тригери

- `packages-20261128-1`
- `packages-20261128-2`

Ці два теги були лише одноразовими тригерами старого package workflow. Нинішній `.github/workflows/package-archives.yml` є read-only `workflow_dispatch` і не приймає `packages-*`. Обидва теги не мають GitHub Release, тому їх можна прибрати, не видаляючи релізні артефакти.

Автоматизація звіряє SHA кожного з цих двох тегів і перевіряє відсутність Release-посилання перед видаленням. Невідомі теги простору `packages-*` не видаляються автоматично — перевірка завершується помилкою.

## Наступні WSM tools релізи

Для наступної версії WSM tools використовувати один тег виду `wsm-tools-<version>`, наприклад `wsm-tools-0.1.0-rcN` після явного призначення номера RC. Не додавати до нього commit SHA, `run-<id>`, дату чи `v2`. Ці значення залишаються в provenance та назві CI run.

Теги старих відкликаних спроб не перейменовуються: вони зберігають історичні прив'язки до своїх commit і Release. Нормалізація застосовується до нових публікацій.
