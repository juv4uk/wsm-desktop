## Навіщо

Питання «чи цей звіт придатний і чи можна рухатися далі» сьогодні вирішує
Python. Перш ніж хтось перепише код, який торкається диска, варто довести, що
саме це рішення вже вміє ухвалювати скомпільований бінарник із тим самим
fail-closed результатом. Тому цей front end реалізує рівно ту частину, яка
нічого не змінює: розбір аргументів, читання звіту, вибір версії схеми,
структурні перевірки preflight, `--classify` і коди виходу.

Бінарник не відкриває блочний пристрій, не викликає системний backend, не
породжує процесів і не потребує root. Єдине, що він пише — stdout і stderr.

## Контракт кодів виходу

Той самий, що в `wsm_install/cli.py`:

| Код | Коли |
| --- | --- |
| `0` | звіт прийнято; для `--classify` — зведення надруковано. `--version` і `--help` теж `0` |
| `2` | відмова: погані аргументи, звіт не читається, невалідний JSON, оголошена версія схеми, яку дерево не знає, або структурна помилка схеми. Також `--execute`, який вимкнено всюди |
| `3` | звіт валідний, але обов'язкові критичні докази не вирішені, тому план не видається. `3` буває лише в `--preflight`; `--classify` на тому самому звіті повертає `0`, бо це діагностика, а не рішення про готовність |

Перший рядок stderr — частина контракту. Для прийнятого звіту це
`WSM hardware preflight — report <report_id>`; для відмови — рядок
`wsm-install: …`, який називає саме ту відмову.

## Що реалізовано

- Розбір аргументів у стилі argparse: `--version`, `-h/--help`, `--preflight`,
  `--report PATH`, `--backend {guix}`, `--dry-run`, `--classify`, `--quiet`,
  `--execute`; підтримуються форми `--opt=value`.
- Читання звіту й розбір JSON власним парсером (`wsmjson.pas`), без fcl-json.
- Вибір схеми за оголошеною версією: `1.0.0` (заморожена) і `1.1.0` (поточна).
  Інша версія — відмова з тим самим текстом, що в Python:
  `wsm-install: unsupported hardware report schema '<v>'; supported: 1.0.0, 1.1.0`.
- Структурні перевірки без бібліотеки JSON Schema: обов'язкові поля,
  `additionalProperties: false` на корені, `environment`, `platform`,
  `privacy`, `device`, `identity`, `driver`, `firmware`, `evidence` і
  елементі `collectors`; форми ідентифікаторів (`report_id`,
  `^(0x)?[0-9a-fA-F]{4}$` для PCI id); режим завантаження
  (`uefi`/`bios`/`unknown`); переліки для категорій, шин, статусів, вимог до
  firmware, рівнів доказів; три `const false` прапорці приватності; легка
  перевірка `date-time`/`date`.
- Правила блокування з `plan.py:build_plan`, бо саме вони вирішують код `3`:
  критичний пристрій зі статусом `unknown`/`not-detected`, обов'язковий
  firmware у стані `missing`/`load-error`, відсутні критичні ролі.
- `--classify`: перенесення `wsm_install/classification.py` (рівні
  `known`/`unknown`, `coverage` завжди `unknown`, докази на рівні можливості,
  а не пристрою).

## Що свідомо не перенесено

Чесний обсяг порту — частина порту, тому це список із наслідками.

1. **Валідація за JSON Schema.** Python вантажить `schemas/*.schema.json` і
   запускає `Draft202012Validator`. Pascal не має бібліотеки схем і не читає
   файл схеми взагалі; він реалізує фіксовану підмножину правил у коді.
   Наслідок для кодів виходу: звіт, який порушує лише правило поза
   підмножиною, тут буде **прийнято**, а Python відхилить. Це fail-open
   розбіжність, і саме тому бінарник поки не замінює Python front end.
   Не перенесено: `uniqueItems` на `criticality`, формат `uri`, повна
   граматика RFC 3339, начинка `cpu`/`gpu`/`network`/`storage`/`display`/
   `recommendations` і `pci_link`, а також `additionalProperties` на цих
   вкладених об'єктах.
2. **Документ чернетки плану.** `build_plan` видає канонічний
   `wsm-install-plan/1` з `plan_sha256`. Pascal його не будує: він відтворює
   правила блокування (код `3`), але не тіло плану, дайджест і
   `device_summary`. Наслідок: stdout на успішному preflight відрізняється,
   код виходу — ні. Замість плану друкується невеликий об'єкт
   `wsm-install-preflight/1`, і stderr прямо каже, що план не видано.
3. **Шляхи, що пишуть файл або тягнуться до диска.** `--install`, `--guided`,
   `--tui`, `--check-env`, `--admission`, `--plan-output`, `--profile-evidence`,
   `--write-plan`, `--schema` і `--target-*` відхиляються з кодом `2` і
   поясненням. Це єдина чесна відповідь: або реалізовувати повністю, або
   відмовити. `--execute` відхиляється тим самим текстом, що в Python.
4. **Текст `--help`.** Вірний за змістом, але не побайтово однаковий з
   argparse: переноси рядків залежать від ширини термінала. Коди відмови
   збігаються.

## Єдине місце, де Pascal суворіший за Python

GPU-пристрій, у якого названо рівно половину пари
`identity.vendor_id`/`identity.device_id`, відхиляється тут. JSON Schema не
вміє висловити «обидва або жодного», тому Python такий звіт приймає. Різниця
одностороння — цей front end відхиляє більше, ніколи менше — і вона записана в
`scripts/check_fpc_cli_parity.py` як `allow_stricter_pascal`, а не схована.

## Як збирається

```sh
guix build -L . -f wsm/packages/wsm-install-fpc.scm
```

Пакет бере лише каталог `wsm_install_fpc/`, компілює `fpc` з
`(gnu packages pascal)` у режимі `objfpc` і ставить один бінарник
`bin/wsm-install-fpc`. Обгортки немає навмисно: паритетний тест має виконувати
саме той файл, який зібрано.

## Як перевіряється паритет

`scripts/check_fpc_cli_parity.py` проганяє обидва бінарники по таблиці звітів
(валідний 1.0.0, валідний 1.1.0, відсутнє обов'язкове поле, відсутнє
`environment`, невідома версія схеми, відсутній `schema_version`, зламаний PCI
id у GPU, половина пари ідентичності GPU, невалідний `boot_mode`, зламаний
JSON, звіт із блокером) у двох режимах — `--preflight` і `--classify` — і
порівнює код виходу та перший рядок stderr.

Нормалізація вузька: відкидається лише текст, який належить мові реалізації —
формулювання декодера JSON, текст `OSError`, переноси рядків argparse. Рішення
(код і місце відмови) не відкидається ніколи.

Сам тест теж перевіряється: `--self-test` запускає harness проти підставних
бінарників і вимагає, щоб він помітив розбіжність у коді, у першому рядку
stderr, у відсутньому рядку, у дозволеній суворості та в fail-open напрямку.
`--python-only` фіксує бік Python: якщо контракт Python зрушить, це буде
названо «python contract drift», а не списано на Pascal.

## Що перевірено, а що ні

Перевірено тут: контракт кодів виходу на боці Python (22 порівняння),
поведінка harness на підставних бінарниках, `make check` для всього, що не
потребує Guix, включно з реєстрацією тестів, документами й Scheme-перевірками
пакета.

Не перевірено тут: компіляція `wsm_install_cli.pas`, збірка пакета Guix,
робота бінарника на реальних звітах. У середовищі, де це писали, немає ні
`fpc`, ні Guix, і `freepascal.org` недосяжний. Твердження «збирається» не
робиться: перший справжній доказ — зелений прогін
[fpc-install-cli.yml](../.github/workflows/fpc-install-cli.yml).
