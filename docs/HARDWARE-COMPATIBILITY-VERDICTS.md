# Політика оцінювання апаратної сумісності

<!-- SPDX-License-Identifier: LicenseRef-Volnist -->

- Статус: **proposed / review draft**
- Власник семантики: [#22 — evidence-based compatibility verdicts](https://github.com/juv4uk/wsm-desktop/issues/22)
- Пов'язані контракти: [#5 — hardware report schema](https://github.com/juv4uk/wsm-desktop/issues/5), [#12 — preflight → plan handoff](https://github.com/juv4uk/wsm-desktop/issues/12), [#16 — driver/runtime firmware evidence](https://github.com/juv4uk/wsm-desktop/issues/16), [#18 — device topology](https://github.com/juv4uk/wsm-desktop/issues/18), [#24 — scenario capability matrix](https://github.com/juv4uk/wsm-desktop/issues/24)

## 1. Призначення

WSM не повинен зводити сумісність комп'ютера до одного непрозорого бала або зеленого індикатора. Оцінка формується **для конкретної функції, конкретного пристрою, конкретного сценарію та конкретного середовища**.

Політика відокремлює три незалежні виміри:

1. **Стан доказів** — що саме відомо про функцію.
2. **Вплив** — наскільки ця функція важлива для обраного сценарію інсталяції.
3. **Рішення сценарію** — чи можна продовжити, потрібне попередження або необхідний додатковий доказ/альтернативний шлях.

Не можна підміняти один вимір іншим. Наприклад, `driver-bound-not-tested` — це стан доказів, а `installation-critical` — рівень впливу.

## 2. Стани доказів

| Стан | Мінімально необхідний доказ | Заборонений висновок |
| --- | --- | --- |
| `supported-tested` | Названий функціональний тест пройшов для конкретної функції/пристрою; зафіксовані метод, середовище, ядро, час і результат | Не означає, що всі режими, порти, периферія чи інші версії ядра працюватимуть |
| `driver-bound-not-tested` | Для конкретної функції є прямий доказ прив'язки драйвера, наприклад її власний sysfs `driver` symlink | Не доводить завантаження firmware, ініціалізацію, продуктивність або функціональність |
| `candidate-only` | Є кандидат драйвера за modalias, модулем або довідковою базою, але немає доказу прив'язки до цієї функції | Не доводить, що модуль є в live image або буде завантажений |
| `known-problem` | Явна помилка, прив'язана до пристрою/функції та поточної сесії: наприклад, помилка probe, явна помилка firmware request або провал обов'язкового функціонального тесту | Не можна виводити з відсутнього запису, відсутнього логу чи відсутності збігу в базі |
| `not-detected` | Успішний і достатньо повний прохід відповідного collector-а не виявив пристрій у задекларованому класі/джерелі | Не означає «несумісний»; не можна застосовувати, якщо покриття collector-а невідоме |
| `not-tested` | Пристрій/функцію виявлено, але відповідний функціональний тест не запускався | Не означає ані успіх, ані помилку |
| `unknown` | Доказ відсутній, недоступний, застарілий, неоднозначний, суперечливий або покриття збору неповне | Ніколи не можна автоматично підвищувати до позитивного стану |

### 2.1 Покриття collector-а: `not-collected` не є негативним результатом

Якщо сценарна матриця або collector повідомляє `not-collected` для певної ролі/класу, compatibility verdict має бути `unknown` із збереженням причини, меж покриття та provenance. Це не `not-tested`, оскільки конкретний пристрій/функцію не було виявлено для запуску тесту; і не `not-detected`, оскільки повний успішний прохід відповідного collector-а не підтверджений. `not-collected` ніколи не може задовольняти critical evidence gate або бути перетвореним на позитивний висновок.

### 2.1 Firmware — окрема послідовність фактів

Не створювати єдине поле/прапорець `firmware_loaded=true` на підставі наявності пакета або файла. Зберігати окремо:

1. firmware package declared;
2. package included in конкретний closure/image;
3. blob present у live rootfs;
4. blob present у initrd/early-boot environment;
5. firmware request observed;
6. explicit request failure або driver-specific success evidence;
7. device driver bound;
8. device/function initialized або functionally tested.

Кожен наступний пункт потребує власного доказу. Відсутність помилки в журналі не є доказом успішного завантаження.

## 3. Рівні впливу

| Рівень | Значення |
| --- | --- |
| `installation-critical` | Без функції неможливо виконати обраний шлях інсталяції або безпечно отримати доступ до цільового ресурсу |
| `first-boot-critical` | Функція потрібна для першого завантаження та базово придатної сесії встановленої системи |
| `important-after-install` | Функція важлива користувачу, але має прийнятний fallback для інсталяції та першого запуску |
| `optional` | Функція не потрібна для обраного сценарію або базової сесії |

Вплив визначається сценарієм, а не назавжди закріплюється за моделлю пристрою. Wi-Fi може бути installation-critical для network-assisted install без Ethernet, але optional для offline install. GPU acceleration може бути important-after-install, тоді як базовий display path достатній для інсталяції.

## 4. Правила прийняття рішення

| Стан доказів | Critical функція без fallback | Important / optional функція |
| --- | --- | --- |
| `supported-tested` | Дозволити продовження в межах перевіреного сценарію; показати scope тесту | Інформаційний результат |
| `driver-bound-not-tested` | Попередження; потрібен тест або незалежно підтверджений fallback до створення підтверджуваного плану | Попередження, не блокувати |
| `candidate-only` | Не вважати шлях доступним; потрібен інший доказ або fallback | Інформаційне попередження |
| `known-problem` | Заборонити план для цього шляху, якщо немає безпечної альтернативи | Попередження; не блокувати всю інсталяцію |
| `not-detected` | Не використовувати функцію як наявну; якщо вона critical і fallback не підтверджено — не дозволяти confirmable plan; запропонувати повторний збір/альтернативу | Інформаційний результат |
| `not-tested` | Не створювати confirmable plan, доки не підтверджено необхідний шлях або fallback | Попередження |
| `unknown` | Evidence gate: зупинити підтвердження плану, запропонувати повторний збір або перевірений fallback | Показати невідомість; не блокувати |

**Evidence gate не є твердженням про несумісність.** Якщо доказів недостатньо для критичної функції, WSM не повинен ані заявляти про несумісність обладнання, ані показувати готовність до небезпечного кроку.

Попередження для optional/important-after-install функції не може непомітно перетворитися на hard-stop. Hard-stop має бути прив'язаний до конкретної вимоги сценарію та відсутності безпечного fallback.

## 4.1 Рівні рішення: чотири, а не два

Матриця вище дає правило для кожної пари «стан × вплив». Для UI, журналу й
інсталятора ці правила згортаються у **чотири названі рівні рішення**. Це не
нова класифікація доказів, а словник для наслідків:

| Рівень рішення | Коли застосовується | Що бачить користувач |
| --- | --- | --- |
| `hard-stop` | Критична для сценарію функція має стан `known-problem`, `unknown`, `not-detected`, `not-tested` або `not-collected`, і безпечного підтвердженого fallback немає | Пояснення, якої саме функції бракує, чому це блокує обраний шлях, і які шляхи лишилися |
| `soft-stop` | Критична функція має `driver-bound-not-tested` або `candidate-only`; fallback існує, але не перевірений | Попередження з конкретним ризиком і явна згода; без згоди план не підтверджується |
| `warn-and-continue` | Функція `important-after-install`, або стан неповний, але шлях інсталяції не залежить від неї | Попередження, яке не блокує |
| `continue` | Функція `optional`, або стан `supported-tested` у межах перевіреного сценарію | Інформаційний рядок, без дії |

**`not-collected` — це не `unknown`, і текст для користувача різний.** Обидва
дають `hard-stop`, але причина інша, і плутати їх небезпечно в обидва боки:

- `unknown` означає «ми подивилися й не знайшли». Формулювання: «цю підсистему
  не вдалося підтвердити».
- `not-collected` означає «ми **не** дивилися»: звіт не покриває цю підсистему.
  Формулювання: «це прогалина у звіті, а не вирок машині — запустіть
  `wsm-hwcheck` на цілі й використайте той звіт».

Назвати неперевірене зламаним — викинути робоче залізо; назвати його
нормальним — пообіцяти те, чого не перевіряли. Тому рішення однакове, а
пояснення — ні.

Два правила, без яких ці рівні перетворюються на гасла:

1. **`hard-stop` не означає «залізо несумісне».** Він означає, що доказів
   недостатньо для цього шляху. Формулювання «ваш комп'ютер не підтримується» —
   заборонене: ми не знаємо цього.
2. **Попередження не може непомітно стати `hard-stop`.** Підвищення рівня
   дозволене лише разом із причиною, прив'язаною до вимоги сценарію, і це
   записується в журнал.

## 4.2 Трирівнева мова для UI — похідна, а не внутрішня модель

У зовнішніх порівняннях (ChromeOS Flex «certified models», сторінки сумісності
вендорів) зручно говорити трьома словами. Для нас це **згортання**, а не
окрема таксономія:

| Зовнішнє слово | Що воно означає в наших термінах |
| --- | --- |
| `certified` | `supported-tested` **плюс** перевірений профіль заліза з evidence bundle ([HARDWARE-PROFILE-EVIDENCE.md](HARDWARE-PROFILE-EVIDENCE.md)); лише тоді, коли є докази для всіх критичних функцій сценарію |
| `known` | `driver-bound-not-tested` або `candidate-only`: компонент розпізнано, конкретна комбінація не тестована |
| `unknown` | `unknown`, `not-tested`, `not-collected` або `not-detected`: доказів немає або вони неповні |

### Строк дії `certified`

`certified` — це не властивість назви моделі й не безстроковий статус. Воно
прив'язане до трійки **байти профілю + реліз ядра + дата доказів** і перестає
діяти, коли змінюється будь-що з цього:

| Що змінилося | Що стається з `certified` |
| --- | --- |
| `profile.scm` (інший SHA-256, ніж у bundle) | анулюється: перевіряли іншу декларацію |
| реліз ядра в профілі | анулюється: докази зібрані на іншому ядрі |
| firmware/мікрокод, названий у звіті | потребує повторної перевірки |
| нічого з переліченого | лишається чинним, доки не сплив строк, визначений політикою профілю |

Порівняння корисне: ChromeOS Flex сертифікує **точну** назву й номер моделі й
публікує для кожної дату «certified until», після якої модель переходить у
`Decertified`. Ми не можемо й не хочемо сертифікувати назви моделей — але
**обмежений строк** у них запозичити варто: доказ, зібраний на ядрі 6.8, не
доводить нічого про ядро 6.9.

Механізм, який це виражає в даних, у нас поки що не вирішений: `verified_on`
фіксує дату, але не строк дії, і додавання поля — це зміна схеми
`wsm-profile-evidence`, яка належить власникам [#171](https://github.com/juv4uk/wsm-desktop/issues/171)/[#5](https://github.com/juv4uk/wsm-desktop/issues/5),
а не цьому документу.

Правило: **внутрішні рішення ніколи не приймаються за трирівневою мовою.**
`certified` не можна вивести з назви моделі, зі збігу в базі або з того, що
«драйвер є». Воно виводиться лише з evidence bundle, і саме тому профілів у
нас поки немає: див. [HARDWARE-PROFILE-EVIDENCE.md](HARDWARE-PROFILE-EVIDENCE.md).

## 5. Якість, свіжість і конфлікти доказів

1. Прямі актуальні спостереження ядра/sysfs/API мають перевагу над збігами за vendor/model у довідковій базі.
2. Збіг у LKDDb, Linux-Hardware.org або іншій базі є кандидатом/історичним підтвердженням, а не доказом runtime binding чи функціональності.
3. Позитивний тест поширюється лише на перевірену функцію та умови: пристрій, ядро, live/installed environment, режим, порт, метод і час.
4. Помилка має бути прив'язана до конкретного пристрою/функції та сесії. Загальний текст журналу не достатній.
5. Суперечливі джерела знижують висновок до `unknown`, доки суперечність не усунуто.
6. Застарілий або отриманий на іншому ядрі доказ не задовольняє поточний critical gate. Його можна зберегти як історичний.
7. Відсутній інструмент, відмовлений доступ, відсутній лог або відсутність запису не є негативним результатом.
8. Кожне похідне рішення має посилатися на джерельні evidence IDs і пояснювати правило, яке його породило.

Сумісність не є постійною властивістю назви моделі: вона залежить від ядра, firmware, конфігурації образу, способу підключення та потрібної функції.

## 6. Приклади

### 6.1 Монітор виявлено, але функцію не перевірено

DRM connector повідомляє `connected`, EDID прочитано, режими перелічено, але активний режим не перевірявся або користувач не підтвердив видимість інтерфейсу.

Результат: **monitor detected + `not-tested`**. Це не `supported-tested`. Фізичний кабельний маршрут також не можна вигадувати з одного connector name.

### 6.2 USB composite device

USB parent і кожен інтерфейс `*:1.N` — окремі функціональні вузли. Driver binding одного інтерфейсу не підтверджує binding його sibling-інтерфейсів.

Результат: окремий evidence state для кожної функції; зв'язок parent/interface має бути підтверджений sysfs topology.

### 6.3 Storage controller без прив'язаного драйвера

Накопичувач або контролер виявлено, але потрібний live kernel driver не прив'язаний. Якщо є явна помилка probe — `known-problem`; якщо доказ неповний — `unknown`. Якщо це єдиний installation-critical шлях до цільового диска, план не можна підтверджувати до усунення проблеми або перевірки fallback.

### 6.4 Wi-Fi driver bound, firmware ambiguous

Є sysfs driver link для Wi-Fi функції, але firmware request/load state неоднозначний і connectivity test не виконувався.

Результат: `driver-bound-not-tested` для драйвера, окремо `unknown` для firmware/runtime function. Не заявляти, що мережа працює.

### 6.5 Database match without local evidence

База даних знайшла підтримку такого vendor/device ID, але локальний collector не побачив bound driver або функціонального тесту.

Результат: `candidate-only` або `unknown`, залежно від локального покриття; ніколи не `supported-tested`.

## 7. Приватність і межі

- Не потрібні serial numbers, MAC addresses, storage UUID/WWN, сирі EDID blobs або інші сталі ідентифікатори для compatibility verdict.
- Не завантажувати hardware probe автоматично; зовнішнє надсилання даних можливе лише як окрема явна opt-in дія.
- Ця політика не запускає модулі, не встановлює firmware, не змінює sysfs, диски, bootloader або конфігурацію системи.
- Жодна рекомендація не виконує deployment action; вона лише пояснює достатність доказів для наступного кроку.

## 8. Сумісність з поточними контрактами

- Поточний report schema v1.0.0 залишається джерелом сирих фактів; цей документ не додає до нього полів.
- Якщо для повного вираження state/impact/relationship потрібні нові поля, вони узгоджуються з власником #5 і вводяться лише у версійованій схемі.
- Handoff #12 зберігає digest звіту та заборону підтвердження плану за невирішених critical unknowns.
- UI #13 показує стан, impact, пояснення та provenance окремо; не використовує один глобальний зелений бал.
- Сценарна матриця #24 визначає, які функції критичні для вибраного шляху; цей документ визначає, як оцінюються докази для кожної функції.

Цей документ є пропозицією для review. Enum-и та поля не слід переносити до schema/collector/UI до погодження з власниками пов'язаних контрактів.
