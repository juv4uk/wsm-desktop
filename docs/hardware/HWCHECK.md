# Збирач апаратних доказів WSM для preflight

<!-- SPDX-License-Identifier: LicenseRef-Volnist -->

- Статус: **прототип v0.3.0** — збирач доказів лише для читання (read-only), а не сертифікація обладнання, оцінка сумісності чи наскрізний функціональний тест.
- Критичний шлях: **так** — інсталятор використовує цей звіт перед записом на диск.

## Запуск

Із кореня репозиторію:

    python3 -m wsm_hwcheck
    python3 -m wsm_hwcheck --output ./hardware-report.json

Файл результату записується лише тоді, коли користувач явно вказує --output. Якщо шлях виводу не задано, JSON-звіт друкується у stdout.

Збирач інвентаризації читає Linux sysfs у /sys і procfs у /proc (або тестові корені, передані через приховані CLI-параметри, призначені лише для тестів). Діагностика середовища виконання додатково читає локальні індекси /lib/modules/<kernel-release>/modules.alias, modules.dep і modules.builtin, а також журнал ядра поточного завантаження через journalctl або dmesg.

Рівень інвентаризації читає локальні sysfs/procfs. Необов'язкова діагностика середовища виконання може викликати фіксовані команди journalctl або dmesg лише для читання, щоб отримати повідомлення ядра поточного завантаження. Збирач не завантажує й не вивантажує модулі, не встановлює пакети, не звертається до мережі, не оновлює firmware, не записує дані на цільові диски, не змінює змінні UEFI та не змінює стан завантажувача.

## Факти для конкретної машини (v0.3)

v0.2 збирав ідентичність PCI та прив'язку драйвера, але не все, що вирішує, чи можна сертифікувати конкретну машину. Один прогін на власній машині дорогий: він означає перезавантаження в Linux. Тому v0.3 додає факти, які читаються лише з sysfs/procfs:

| Факт | Поле звіту | Джерело |
| --- | --- | --- |
| Режим завантаження UEFI або legacy BIOS | `environment.boot_mode` + `environment.boot_mode_evidence` | наявність `/sys/firmware/efi`; відсутність на x86 із DMI — це `bios`, без DMI — `unknown` |
| Версія, дата й release BIOS | `environment.platform.bios_version`, `bios_date`, `bios_release` | `/sys/class/dmi/id/*`; дата нормалізується з `MM/DD/YYYY`, нерозбірлива — не записується |
| Мікрокод і stepping CPU | `devices[].cpu.microcode`, `stepping`, `family`, `model_number` | `/proc/cpuinfo`, резервно `/sys/devices/system/cpu/cpu0/microcode/version` |
| PCI-ідентичність GPU і прив'язка драйвера | `devices[].identity` + `devices[].driver` | `/sys/bus/pci/devices/<bdf>/vendor`, `device`, `driver`; відсутній symlink — `none-known`, а не `unknown` |
| Boot VGA, DRM-вузли та ширина PCIe лінка | `devices[].gpu` | `boot_vga`, `drm/card*`, `current_link_speed`, `current_link_width` |
| Модель NIC | `devices[].identity.model` і `manufacturer` | локальний `pci.ids` як offline-база; немає файла — назви лишаються невідомими |
| Інтерфейси NIC | `devices[].network` | `/sys/class/net/*`, лише ті, чий `device` веде саме до цієї PCI-функції |
| Топологія накопичувачів | `devices[].storage` | `/sys/block/<dev>/size`, `queue/*`, `removable`, `ro`, розділи, шина з предків sysfs |

Правило незмінне: кожен факт або спостережений, або перелічений в `unavailable` відповідного об'єкта. Немає значення за замовчуванням, немає «приблизно SATA», немає MAC-адреси чи серійного номера.

### Чого v0.3 свідомо не збирає

- Таблицю розділів (GPT/MBR), типи файлових систем і записи завантажувача — для цього потрібні block device або зовнішні утиліти, а збирач обіцяє не торкатися дисків.
- Прапорці CPU й рівень ISA — це окремий контракт `wsm-cpu-isa/1` (`python3 -m wsm_hwcheck.isa`), а не поле звіту.
- MAC-адреси, серійні номери, UUID, WWN — заборонені профілем приватності strict-local.
- Декодування EDID і зв'язок «конектор → GPU» — це #18.
- Runtime firmware blob'и, крім випадку, коли ядро саме про них повідомило.

## Рівень інвентаризації (v0.1)

- Поля моделі/виробника CPU, доступні через /proc/cpuinfo.
- Дані платформи DMI та моделі материнської плати, без файлів із серійними номерами.
- Ідентифікатори PCI, modaliases і прив'язка драйверів до PCI-функцій.
- Лише ідентифікатори батьківських USB-пристроїв; класи складених USB-інтерфейсів та прив'язки драйверів для окремих інтерфейсів у v0.1 не збираються.
- Модель/виробник блочних пристроїв зберігання та прив'язка драйвера ядра, якщо це доступно через sysfs.
- Стан підключення конекторів DRM і режими, які надає ядро, якщо вони доступні; ідентифікація монітора за EDID та явні зв'язки між конектором і GPU у v0.1 не збираються.

## Докази щодо драйверів і firmware під час виконання (v0.2)

- Зіставляти PCI/USB modaliases із локальним файлом /lib/modules/<kernel-release>/modules.alias запущеного ядра, а потім підтверджувати кандидатні назви за допомогою modules.dep разом із розв'язаним файлом модуля на диску або через modules.builtin. Збіг alias без підтверджувального артефакту модуля не вважається доступним драйвером, якщо обидва індекси повні.
- Спостерігати назви завантажених модулів у /sys/module та зберігати різницю між кандидатом, доступним у поточному дереві ядра, завантаженим, але не прив'язаним модулем і драйвером, прив'язаним через sysfs. Якщо індекси модулів неповні, доступність лишається невизначеною, а не позначається як непідтримувана.
- Перевіряти журнал ядра поточного завантаження за допомогою фіксованих аргументів journalctl, із dmesg як резервним варіантом. Вивід потоково обробляється через буфер останніх 2 MiB, обсяг stderr обмежено, кожен процес має жорсткий timeout; обрізання виводу позначається окремо.
- Повідомлення налагодження direct-loading відображається як available-not-confirmed-loaded: воно показує, що blob було прочитано в буфер запиту firmware. Версія firmware, яку повідомляє драйвер як завантажену, також відображається як available-not-confirmed-loaded, оскільки це не доводить прийняття пристроєм або його ініціалізацію. Цей прототип навмисно не видає loaded на підставі таких загальних сигнатур; цей стан слід залишити для перевіреного позитивного сигналу, специфічного для пристрою.
- Зберігати нормалізовані підсумки, а не сирі рядки журналу ядра. Відсутність доступу до журналу або відсутність події, яку можна пов'язати з пристроєм, залишає стан firmware як unknown.

## Відомі прогалини покриття v0.1

- Функції складених USB-пристроїв не перелічуються як окремі записи інтерфейсів `*:1.N`. Батьківське значення `bDeviceClass` `00` залишається `other`; прив'язка драйвера на рівні інтерфейсу не заявляється. Див. #18 щодо окремої роботи над версіонованою топологією.
- Записи конекторів DRM не є ідентичністю фізичного монітора. v0.1 не декодує EDID і не пов'язує конектор із GPU-власником; ці зв'язки лишаються unknown, доки не буде реалізовано явні докази топології.
- Спостережений стан конектора або активний режим є лише доказом інвентаризації/середовища виконання. Він ніколи не видається як успішний функціональний тест passed.

## Чого це поки не доводить

- Чи може мережевий інтерфейс під'єднатися до точки доступу або отримати доступ до Інтернету.
- Чи здатний GPU стабільно підтримувати запитаний режим дисплея або прискорювати робоче середовище.
- Чи працюють наскрізно вивід/ввід аудіо, Bluetooth, вебкамера, призупинення/відновлення або керування живленням.
- Чи потребує пристрій певного runtime firmware blob, якщо не було спостережено відповідного повідомлення ядра поточного завантаження.
- Чи відповідає зовнішній звіт для схожої моделі фактичній ревізії плати та версії ядра.

Ці властивості лишаються unknown або not-tested. Прив'язаний драйвер не подається як успішно перевірена функція.

Реалізація firmware loader у Linux створює загальне повідомлення налагодження `direct-loading`
до того, як запит firmware остаточно прив'язується до пристрою; тому WSM не класифікує це
повідомлення як підтвердження успішного завантаження. Див.
[upstream firmware loader](https://github.com/torvalds/linux/blob/master/drivers/base/firmware_loader/main.c)
та [документацію API request_firmware](https://www.kernel.org/doc/html/latest/driver-api/firmware/request_firmware.html).

## Звіт і приватність

Звіт відповідає [формату апаратних доказів WSM, версія 1](REPORT-FORMAT.md). Він використовує випадковий ідентифікатор для кожного запуску й не містить серійних номерів, MAC-адрес, UUID, імен хостів, імен користувачів, IP-адрес або WWN накопичувачів. У v1 немає мережевих запитів і вивантажень. Журнали ядра обробляються локально; у звіт потрапляють лише нормалізовані підсумки, пов'язані з пристроєм, а не сирі рядки журналу.

Реалізація Python не має сторонніх залежностей часу виконання. Для діагностики журналу ядра вона за можливості використовує наявні в системі команди journalctl або dmesg; якщо жодна з них недоступна або не може читати журнал, звіт фіксує це й зберігає стани unknown. Інструменти upstream, як-от hwinfo, hw-probe, посилання на LKDDb, edid-decode та libdisplay-info, залишаються необов'язковими постачальниками доказів до завершення перевірки пакетів, приватності, ліцензування та середовища виконання.
