# CPU ISA evidence: рівні x86-64

<!-- SPDX-License-Identifier: LicenseRef-Volnist -->

- Статус: **реалізовано, контракт v1**: Python reference (`wsm_hwcheck/isa.py`) і native FPC CLI (`tools/pascal/wsm_cpu_isa.pas`, tool version `0.1.2`)
- Критичний шлях: **ні** — дослідницький контракт поверх звіту v1.0.0
- Задача: [#148](https://github.com/juv4uk/wsm-desktop/issues/148)
- Батьківське рішення: [ADR 0007](../decisions/0007-clear-linux-principles.md)

## Навіщо окремий контракт, а не поле у звіті

Схема звіту `1.0.0` версіонована, і додавання поля в неї зламало б усіх, хто
валідовує звіт своєю копією схеми. Тому ISA-докази живуть окремим артефактом зі
своєю версією (`wsm-cpu-isa/1`) і своїм джерелом — тим самим `/proc/cpuinfo`,
який колектор уже читає.

## Що саме обчислюється

Рівні x86-64 з psABI: **кумулятивні** набори ознак.

| Рівень | Що додає | Приблизно відповідає |
| --- | --- | --- |
| `x86-64-v1` | базова SSE/SSE2 | базова x86-64 ABI |
| `x86-64-v2` | CMPXCHG16B, LAHF/SAHF, POPCNT, SSE3, SSSE3, SSE4.1, SSE4.2 | Intel Nehalem (2008), AMD Bulldozer (2011) |
| `x86-64-v3` | AVX, AVX2, BMI1, BMI2, F16C, FMA, LZCNT, MOVBE, OSXSAVE | Intel Haswell (2013), AMD Zen |
| `x86-64-v4` | AVX-512 F/BW/CD/DQ/VL | Intel Skylake-SP та новіші реалізації з повним набором |

**Кумулятивність — головне правило.** Процесор з AVX, але без AVX2 — це `v2`, а
не «майже v3». Рівень зараховується лише коли є **всі** ознаки цього й усіх
нижчих рівнів.

## Джерело та семантика доказу

Модуль читає лише `/proc/cpuinfo`; він не запускає `lscpu`, CPUID/MSR утиліти,
мережеві команди або benchmark-и. Враховується **перетин flags усіх processor
blocks**, які повідомляє procfs. Це консервативна machine-wide межа: процес може
переміщуватися між логічними CPU, тому рівень для безпечного runtime dispatch
має бути доступним на кожному з них.

Якщо хоча б один processor block не містить непорожнього поля `flags`, модуль
відмовляється формувати system-wide verdict із кодом
`cpuinfo.flags-incomplete` або `cpuinfo.flags-unavailable`. Він не підміняє
відсутні дані порожнім списком і не видає `x86-64-v1` як підтверджену верхню
межу.

Непорожній блок без ідентифікатора `processor` серед кількох блоків також
спричиняє `cpuinfo.processor-block-incomplete`: parser не може мовчки відкинути
частину джерела й обчислити intersection лише з решти. Fallback для
альтернативного формату лишається тільки для одного блока без `processor`.

Усі ці відмови означають «даних недостатньо» (`unknown`/`not-assessed`) для
споживача контракту, а не доказ несумісності (`unsupported`).

Важливо: сам Linux описує `/proc/cpuinfo` flags як **неповний** інтерфейс.
Наявність прапорця означає, що ядро його знає й експонує як доступний стан.
Відсутність прапорця **не доводить**, що кремній не має відповідної можливості:
ядро може бути застарілим, не знати прапорця або не експонувати його через
firmware/build/runtime policy. Тому `highest_supported` у цьому артефакті —
найвищий рівень, підтверджений спільним kernel-exposed набором, а не
інвентаризація всіх фізичних можливостей CPU.

Джерело: [Linux kernel — x86 Feature Flags](https://www.kernel.org/doc/html/latest/arch/x86/cpuinfo.html).

## Чого цей контракт не робить

- **Не вмикає нічого.** Рівень — це доказ, а не прапорець збірки.
- **Не обіцяє пришвидшення.** Для більшості навантажень різниця між v2 і v3 —
  кілька відсотків; помітна вона у стисненні, криптографії та числовому коді, де
  бібліотеки й так диспетчеризують у рантаймі.
- **Не визначає CPU за vendor/model.** Лише за ознаками.
- **Не читає сирі CPUID/MSR.** Поточний scope — лише kernel-exposed procfs flags.

## Пастка AVX/OSXSAVE

Рівні v3/v4 потребують повного набору ознак і стану, який ОС експонує для
використання AVX-family. Відсутній `osxsave` означає, що відповідний рівень не
підтверджений цим джерелом. Це **не** доказ того, що апаратна підтримка відсутня.

## Запуск

```sh
python3 -m wsm_hwcheck.isa --compact
python3 -m wsm_hwcheck.isa --report hw.json    # перехресна перевірка зі звітом
wsm-cpu-isa --compact
wsm-cpu-isa --report hw.json                   # native FPC CLI, той самий JSON-контракт
```

Для Guix native build доступний окремий пакет `wsm-cpu-isa-fpc`; він встановлює лише `wsm-cpu-isa`, а FPC залишається build-time input.

На машині з іншою архітектурою (наприклад `aarch64`) обидві реалізації відмовляють з кодом
`isa.not-x86` до читання x86-specific `flags`: рівні x86-64 до неї не
застосовні, і вигадувати відповідник не варто.

## Як це вплине на профілі WSM

Базовий профіль лишається `x86-64-v1`: переносимість важливіша за кілька
відсотків. Оптимізовані варіанти — окреме рішення, яке вимагає benchmark-у й
безпечного fallback (див. [ADR 0007](../decisions/0007-clear-linux-principles.md)).
