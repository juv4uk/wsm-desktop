## Призначення

Звіт — це backend-нейтральний запис доказів, який створює live-середовище перед встановленням. Він не є сертифікацією обладнання, результатом бенчмарку або загальною оцінкою сумісності.

Він зберігає різницю між спостереженнями, зробленими на поточній машині, записами із зовнішніх баз і функціями, які справді перевіряли.

## Версіювання

Перша схема — 1.0.0, цільова версія JSON Schema — Draft 2020-12.

- Несумісна зміна збільшує мажорну версію.
- Сумісне додавання необов'язкового поля збільшує мінорну версію й вимагає опублікованої схеми саме для цієї мінорної версії та явної підтримки з боку споживача.
- Уточнення, що не змінюють поведінку валідації, збільшують патч-версію.
- Виробники записують точну версію схеми. Споживачі обирають валідатор саме для цієї версії й відхиляють непідтримувані версії з поясненням, а не читають їх мовчки неправильно.

Схема v1.0.0 встановлює `additionalProperties: false` для своїх закритих об'єктів. Тому споживач v1.0.0 **не** толерує невідомі властивості загалом. Нове необов'язкове поле приймається лише після випуску відповідної ревізії схеми й підтримки в споживачі. Не заявляйте сумісність із майбутніми полями, якої вибраний валідатор схеми не реалізує.

### Поточна ревізія: 1.1.0

Поточна опублікована схема — **1.1.0** ([hardware-report.schema.json](../../schemas/hardware-report.schema.json)). Вона додає лише необов'язкові поля, тому звіт 1.0.0 описує підмножину формату і лишається чинним.

Заморожена копія 1.0.0 лежить поруч: [hardware-report-1.0.0.schema.json](../../schemas/hardware-report-1.0.0.schema.json). Звіт перевіряється **тією схемою, яку він сам оголошує** (`wsm_install/report_schema.py`), а не поточною: поточна пінить `schema_version` на 1.1.0 і відхилила б валідний звіт 1.0.0. Версія, якої немає серед опублікованих, відхиляється з назвою версії в повідомленні, а не читається «приблизно».

Що додає 1.1.0:

- `environment.boot_mode_evidence` — чому `boot_mode` саме такий (яке джерело було присутнє або відсутнє);
- `environment.platform.bios_release`, а `bios_date` тепер заповнюється з DMI й нормалізується з `MM/DD/YYYY` у ISO-дату;
- `devices[].cpu` — `family`, `model_number`, `stepping`, `microcode`, `logical_processors`;
- `devices[].gpu` — `boot_vga`, `drm_cards`, `pci_link`;
- `devices[].network` — інтерфейси, чий sysfs-зв'язок веде саме до цієї PCI-функції;
- `devices[].storage` — `capacity_bytes`, розміри логічного й фізичного сектора, `rotational`, `removable`, `read_only`, `transport`, `partitions`.

Кожен із цих об'єктів має `unavailable`: перелік фактів, яких жодне читабельне джерело не дало. Це і є `unknown`, виражений явно. Заповнене «приблизне» значення замість `unavailable` — дефект, а не зручність.

## Модель доказів

Для кожного пристрою зберігайте окремі факти:

- discovery: discovered / not-detected / unknown;
- driver: bound / module-loaded-unbound / available-only / none-known / error / not-applicable / unknown;
- runtime firmware: loaded / available-not-confirmed-loaded / missing / load-error / not-needed / unknown;
- кожен функціональний тест: passed / failed / partial / not-run / unsupported / unknown.

Кандидатний драйвер, який повідомив індекс пакетів або база конфігурації ядра, не означає, що запущене ядро його завантажило чи прив'язало.

Завантаження runtime firmware — це не те саме, що оновлення firmware пристрою. Успішна здатність оновити firmware пристрою нічого не каже про те, чи має драйвер ядра потрібний йому runtime-блоб.

Функціональний тест документує свій метод і результат. Read-only інвентаризаційна перевірка може довести, що роз'єм існує, але не те, що наскрізне завдання працює.

## Походження доказів

Кожен елемент доказів записує свій вид, джерело/інструмент і необов'язкові версію/URL, час спостереження, мітку впевненості, стислий підсумок і необов'язкове посилання.

Використовуйте `confirmed` лише для безпосередньо спостереженого факту або відтворюваного тесту. Запис із зовнішньої бази зазвичай лишається `strong` або `limited` залежно від точності збігу обладнання й ядра. Використовуйте `unknown`, коли якість джерела або збіг неясні.

## Приватність

Профіль strict-local є типовим. Звіти не повинні містити серійних номерів, MAC-адрес, UUID, імен хостів, імен користувачів, IP-адрес або WWN носіїв. Ідентифікатор звіту — випадковий ідентифікатор конкретного звіту, а не стабільний ідентифікатор хоста.

Мережеве вивантаження у v1 — false. Робочий процес експорту мусить створити окрему санітизовану копію і показати категорії даних до того, як просити згоду. Ніколи не вважайте редагування upstream-інструмента достатнім.

## Дані дисплея

Запис дисплея розрізняє ідентичність монітора, декодовану з EDID, ідентичність роз'єму й стан з'єднання, заявлені режими, активний режим, спостережений через DRM/KMS, і активну частоту оновлення, де вона доступна.

Заявлені режими не є доказом того, що кожен режим працює через фактичний шлях GPU, роз'єму, кабелю й монітора.

## Синтетичні фікстури

Фікстури в цьому каталозі синтетичні й не містять звіту з реальної машини:

- [desktop-observed.json](../../tests/fixtures/hardware/desktop-observed.json)
- [missing-firmware.json](../../tests/fixtures/hardware/missing-firmware.json)
- [unknown-incomplete.json](../../tests/fixtures/hardware/unknown-incomplete.json)

Фікстури лишаються у форматі 1.0.0 навмисно: вони доводять, що старий звіт і далі проходить валідацію власною схемою. Факти 1.1.0 перевіряються синтетичним деревом sysfs у `tests/test_hwcheck.py` і тестовими документами в `tests/test_hardware_report.py`, а не новою фікстурою з реальної машини.

## Настанови щодо реалізації

Колектори тримають сирі спостереження окремо від похідних рекомендацій. Рекомендації посилаються на докази й зазначають впевненість. Ніколи не перетворюйте статус `unknown` на відмову лише тому, що джерело пошуку або необов'язкова утиліта недоступні.

## Нативні інструменти Free Pascal

Для зменшення runtime closure WSM має окремі нативні Guix-пакети:

- `wsm-hwcheck-fpc` — read-only колектор PCI identity та прямого driver binding із sysfs. Він формує повний конверт Hardware Evidence Report 1.1.0, але збирає лише PCI-пристрої; CPU, USB, block, DRM, firmware logs та функціональні тести в цьому зрізі не збираються. Відсутність цих фактів лишається явно невідомою, а не домислюється.
- `wsm-classify-fpc` — діагностичний підсумок підсистем за тим самим контрактом, що й `wsm_install/classification.py`. `certified` завжди дорівнює нулю; результат не є дозволом на інсталяцію.
- `wsm-partition-fpc` — read-only GPT-планувальник: формує команди як дані, перевіряє цільовий диск, підтвердження оператора та дрейф розміру; не виконує `sgdisk` і не змінює таблицю розділів.
- `wsm-profile-fpc` — попередня семантична перевірка evidence bundle: версія формату, синтаксис відносних шляхів, дублікати, наявність артефактів і хоча б одна функція зі статусом `pass`. Це не повний JSON Schema validator і не перевіряє SHA-256; результат прямо позначає digest verification як `delegated`, тому пакет не замінює повний Python validator.
- `wsm-preflight-fpc` — перевіряє інструменти, Guix, права доступу, точку монтування, опис системи, hardware report та ISA до інсталяції; розрізняє `fail` і `not-run` та не змінює систему.

Усі п’ять пакетів використовують `LicenseRef-Volnist` / `ВОЛЬНІСТЬ`. FPC є лише build-time `native-input`, а не runtime dependency; жоден із пакетів не тягне Python interpreter.

Збірка локально з установленим FPC 3.2.2: `make -C tools/pascal clean all`. Перевірка усіх п’яти пакетів у Guix: `make build-fpc-packages`. Workflow **Free Pascal build** компілює усі п’ять executable, перевіряє JSON Schema 1.1.0 і порівнює PCI-колектор та класифікатор з Python-reference; для partition/profile запускає CLI runtime-тести. До успішної компіляції й runtime перевірок пакети не вважаються перевіреними.

Це зменшений native backend, а не повна заміна Python-колектора. Розширювати його слід окремими зрізами — CPU/ISA, USB, block/storage, DRM/display та runtime diagnostics — кожен із parity-тестами до увімкнення в системному профілі.
