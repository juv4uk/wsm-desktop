# Протокол перевірки сумісності дисплеїв і моніторів WSM

<!-- SPDX-License-Identifier: CC-BY-SA-4.0 -->

- Статус: **proposed / validation protocol**
- Пов'язана задача: [#20](https://github.com/juv4uk/wsm-desktop/issues/20)
- Батьківська матриця: [#8](https://github.com/juv4uk/wsm-desktop/issues/8)
- Контракти доказів: [#5 — hardware report](https://github.com/juv4uk/wsm-desktop/issues/5), [#18 — topology](https://github.com/juv4uk/wsm-desktop/issues/18)
- Межа інсталятора: [#12 — installer handoff](https://github.com/juv4uk/wsm-desktop/issues/12)

## 1. Мета

Цей протокол визначає, як збирати й оцінювати докази щодо графічного адаптера, DRM/KMS connector-ів і фізичних дисплеїв до встановлення WSM.

Він не визначає нову JSON-схему та не реалізує collector. Протокол споживає наявні звіти й явні зв'язки з #18. Якщо зв'язок GPU → connector → display не представлений доказом, він залишається **unknown**.

Головне правило: **заявлена монітором можливість ≠ можливість, яку надає поточний драйвер ≠ реально перевірений режим виводу**.

## 2. Рівні доказів

| Рівень | Що спостерігаємо | Що можна стверджувати | Чого стверджувати не можна |
| --- | --- | --- | --- |
| D0 — GPU inventory | GPU, PCI ID, kernel, driver binding | GPU виявлено; вказаний драйвер прив'язаний, якщо це підтверджено джерелом | Що DRM/KMS або вивід зображення працює |
| D1 — DRM topology | DRM card, connector, явні зв'язки з GPU | Які connector-и експонує поточний kernel/driver | Що до connector-а фізично підключений конкретний монітор, якщо немає окремого доказу |
| D2 — sink observation | connector status, EDID blob, kernel-exposed modes | Ядро повідомляє про стан connector-а та доступні йому режими | Що кожен режим EDID підтримується GPU/кабелем або успішно працює |
| D3 — active runtime state | активний CRTC/connector/mode через відповідний userspace/compositor інтерфейс | У поточній сесії повідомляється активний режим | Що зображення візуально коректне або стабільне |
| D4 — user-visible functional check | Користувач підтвердив видиме зображення на потрібному фізичному дисплеї у записаному режимі | Конкретна комбінація GPU/connector/display/mode пройшла обмежену функціональну перевірку | Загальну сумісність з усіма режимами, кабелями, портами чи майбутніми ядрами |

Результат має зберігати рівень доказу та джерело. D4 не можна генерувати автоматично з D0–D3.

## 3. Безпечний збір read-only evidence

Усі команди нижче призначені для читання. Їх доступність і точний формат залежать від live image, прав користувача, ядра та версії інструмента. Перед використанням записати версії інструментів; не встановлювати пакунки й не додавати binary caches лише заради preflight.

### 3.1 Контекст системи

~~~sh
uname -r
cat /proc/cmdline
lspci -nnk
~~~

Зберігати тільки потрібні для відтворення поля: kernel release, boot parameters, PCI vendor/device/subsystem IDs, GPU class та фактичний driver binding. Перед експортом видалити hostname та інші локальні ідентифікатори, якщо вони потрапили до журналу.

### 3.2 DRM connector-и через sysfs

~~~sh
for d in /sys/class/drm/card*-*; do
  [ -d "$d" ] || continue
  printf '%s\n' "$d"
  [ -r "$d/status" ] && printf 'status: ' && cat "$d/status"
  [ -r "$d/enabled" ] && printf 'enabled: ' && cat "$d/enabled"
  [ -r "$d/modes" ] && { printf 'kernel modes:\n'; cat "$d/modes"; }
done
~~~

Це snapshot kernel-exposed стану. Каталог або назва connector-а — не стабільний hardware identifier. status=connected означає, що драйвер вважає sink підключеним; це не перевірка якості сигналу чи видимого зображення. modes — режими, які ядро експонує для connector-а, а не список функціонально перевірених режимів.

### 3.3 DRM/KMS inventory через libdrm

Якщо modetest уже присутній у live image, спочатку зафіксувати modetest --help та версію пакунка. Для інвентаризації використовувати лише query options, наприклад:

~~~sh
modetest -c -e -p
~~~

Ці опції призначені для переліку connectors, encoders, CRTCs і planes. Не використовувати режими тестування/зміни стану на етапі read-only preflight: зокрема не передавати -s, -P, -w, -r або інші параметри, що встановлюють mode, plane чи property. Якщо команда вимагає привілеїв або не може безпечно працювати поруч із активним compositor-ом, пропустити її та позначити джерело як недоступне; не зупиняти графічну сесію.

Вивід modetest залежить від версії libdrm і драйвера. Не парсити його як стабільний машинний API без окремого versioned adapter-а.

### 3.4 EDID

EDID належить конкретному DRM connector-у. Для діагностики можна передати один connector EDID-файл у edid-decode, якщо ця утиліта вже встановлена:

~~~sh
edid-decode --help
edid-decode --hide-serial-numbers --replace-unique-ids --skip-hex-dump /sys/class/drm/cardX-CONNECTOR/edid
~~~

Перед використанням перевірити, що локальна версія підтримує наведені опції. Не об'єднувати EDID кількох connector-ів в один потік. Не зберігати raw EDID у публічному профілі. Якщо потрібен локальний діагностичний файл, він залишається приватним і видаляється після перевірки за правилами власника системи.

**Важливо:** kernel DRM/KMS документація рекомендує userspace брати режими з KMS properties, а не повторно обчислювати їх із EDID: ядро може застосовувати quirks, limits та fixups. Тому EDID decoder — допоміжне джерело ідентифікації/діагностики, а не авторитетний список режимів для рішення інсталятора.

### 3.5 Активний режим

Активний режим треба зчитувати з інтерфейсу, який відповідає поточній графічній сесії:
- X11: xrandr --current, якщо команда доступна та сесія справді X11;
- Wayland: відповідний read-only інтерфейс/утиліта конкретного compositor-а, якщо він доступний;
- DRM-only/live fallback: зафіксувати, що active mode не зібрано, якщо немає перевіреного read-only джерела.

Не трактувати EDID preferred/native timing або sysfs modes як поточний активний режим. Не запускати mode-setting команду лише для того, щоб отримати «кращий» доказ.

## 4. Функціональна перевірка користувачем

D4 дозволений лише після окремої, явно погодженої перевірки. Вона не є частиною автоматичного inventory.

Для кожного фізичного дисплея окремо:
1. Переконатися, що користувач знає, який саме екран перевіряється; не визначати фізичний екран за connector name або порядком.
2. Записати GPU, connector ID (report-local), явний topology edge, модель/виробника монітора лише якщо це отримано з дозволеного privacy-safe поля, кабель/перехідник лише зі слів користувача.
3. Записати фактичний активний режим, частоту, масштабування, pixel format / color depth, якщо ці дані доступні з поточної сесії.
4. Попросити користувача підтвердити, що зображення є на правильному екрані, читається, не обрізане та не має помітних артефактів, мерехтіння чи періодичних втрат сигналу під час короткого звичайного використання.
5. Позначити перевірку як **pass** тільки для цієї конкретної комбінації. Якщо користувач не може підтвердити результат, немає доступу до екрана або режим не перевірявся — **not-tested**, а не pass.
6. Не змінювати постійні налаштування, firmware, boot options або фізичні підключення без окремої згоди.

Для multi-monitor:
- кожен connector/display перевіряється окремо;
- додатково фіксується саме одночасна комбінація екранів, їхні режими й розташування;
- успіх одного дисплея не переноситься на інші;
- невідомий topology edge не заповнюється евристично.

Перевірка одного режиму не доводить роботу всіх advertised modes. Для ширшого профілю повторювати перевірку лише для конкретно заявлених цільових режимів і комбінацій.

## 5. Критерії результату

| Результат | Критерій |
| --- | --- |
| observed | Джерело прочитало відповідний факт; це не functional pass |
| pass | Є D4 user-visible підтвердження для точно записаної конфігурації |
| fail | Перевірка виконана, але зображення відсутнє або має задокументований дефект |
| not-tested | Перевірку не виконували або немає користувацького підтвердження |
| unknown | Не вистачає доказів для висновку, зокрема немає надійного topology link |

Невдале читання EDID саме по собі не означає, що монітор несумісний. Відсутність connector-а, який можна ідентифікувати, також не доводить відсутність фізичного порту: це може бути обмеження поточного драйвера, kernel, firmware або live image.

## 6. Мінімальний запис профілю

Один запис на кожну перевірену конфігурацію:

| Поле | Значення |
| --- | --- |
| Profile ID | Локальний випадковий ID профілю, без серійного номера |
| Environment | VM або physical; ніколи не змішувати |
| Kernel / driver | Точні версії та фактичне binding evidence |
| GPU | PCI IDs, report-local device ID |
| DRM connector | Report-local ID, тип і status observation |
| Display | Privacy-safe vendor/model, якщо відомі; інакше unknown |
| Topology evidence | Relationship ID/type/source або unknown |
| Advertised modes | KMS-exposed modes; EDID parse — окрема довідкова інформація |
| Active mode | Фактичний режим із джерелом або not-collected |
| Functional check | Pass/fail/not-tested, хто підтвердив і коли |
| Tested combination | Для multi-monitor — усі дисплеї й одночасні режими |
| Limitations | Кабель/adapter unknown, HDR/VRR not-tested, інші обмеження |
| Provenance | Інструмент і версія, команда, timestamp, evidence source |

Не включати serial number монітора, raw EDID, hostname, MAC, UUID, WWN, IP чи інші стабільні ідентифікатори. Зовнішнє завантаження probe data не є частиною цього протоколу.

## 7. Межі висновку для installer-а

- D0–D2 можуть допомогти пояснити, що виявлено та які можливості експонує поточний стек.
- D3 показує runtime state поточної сесії, але не гарантує візуальної коректності.
- D4 підтверджує лише протестовану комбінацію й не дає універсального сертифіката сумісності.
- Unknown display path може бути критичним для інтерактивного встановлення, але installer має враховувати реальні альтернативи (інший перевірений дисплей або доступний інший сценарій), а не глобально оголошувати весь комп'ютер несумісним.
- Невідомі topology relationships залишаються unknown до появи evidence у версійованому звіті.

## 8. Джерела

- Linux kernel, [DRM/KMS documentation](https://docs.kernel.org/gpu/drm-kms.html): connector status, modes, EDID property та правило використовувати kernel-exposed KMS properties замість повторного парсингу EDID modes.
- Linux kernel, [DRM UAPI](https://docs.kernel.org/gpu/drm-uapi.html): userspace-facing connector/property semantics.
- libdrm modetest: query/test options залежать від версії; локальний modetest --help є обов'язковою перевіркою доступних опцій перед використанням.
- edid-decode: перевіряти підтримку privacy flags у локальній версії через edid-decode --help; не публікувати raw EDID.

Цей документ є протоколом проєкту, а не твердженням, що наведені тести вже виконані на фізичному обладнанні WSM.
