## `WSM-Desktop-0.1.0-rc6-Minimal-Live.iso`

**Джерело:** чернетка релізу `0.1.0-rc6-minimal-live` (не опублікована).
**Статус:** перевірено; публікація потребує рішення власника.

Це **перший** носій проєкту, для якого доведено не лише завантаження, а й
роботу інсталятора всередині гостьової системи.

### Що перевірено

| Перевірка | Результат |
| --- | --- |
| Контрольна сума | **збігається**: `59dad1c0f987401ab3644c6cf93445f22ff7fbfae6b47010c2611dcaa5702f99` |
| Розмір | 911 370 240 байт (869 MiB) |
| Формат | справжній ISO9660 (`CD001`) |
| Завантажувальні записи | El Torito з обома прошивками |
| Завантаження в BIOS | **pass**, маркер `WSM_LIVE_READY` |
| Завантаження в UEFI | **pass**, маркер `WSM_LIVE_READY` |
| **Запуск інсталятора в гості** | **pass**, маркер `WSM_INSTALLER_OK` |
| Вміст | `wsm_install`, `tui.py`, `guided.py`, `agent.py`, `classification.py` |

Маніфест релізу: `acceptance: {bios: pass, uefi: pass, installer: pass}`.

### Чому це важливо

У попередніх носіях приймання перевіряло лише маркер завантаження, і в
boot-свідченнях стояло `guest_installer_execution: false`. Тобто «система
стартує» і «в системі є робочий інсталятор» були різними фактами, і другий не
перевірявся — саме так одного разу вийшов образ без трьох frontend-ів.

Тепер live-профіль запускає справжній entrypoint і окремо перевіряє імпорти,
а конвеєр вимагає обидва маркери в обох прошивках.

### Межа доказу

`WSM_INSTALLER_OK` означає: обгортка й entrypoint стартують, а `jsonschema`,
`wsm_install.cli`, `classification`, `partition` і `profile` імпортуються.

Це **не** доводить, що TUI малюється: для цього потрібен термінал. І не
доводить, що встановлення на конкретне залізо пройде — для цього потрібен
профіль із evidence.

### Машиночитний вердикт

[`artifacts/iso-verdict-0.1.0-rc6-minimal-live.json`](artifacts/iso-verdict-0.1.0-rc6-minimal-live.json)

`overall: incomplete` — чесний результат: у середовищі перевірки немає QEMU,
тому `boot-bios` і `boot-uefi` стоять `not-run`. Самі ці два факти доводить
конвеєр, і його свідчення наведені вище.

## `wsm-desktop-kde-hardened-20261125.iso`

**Джерело:** реліз `0.1.0-rc2-live-iso`.

### Що перевірено

| Перевірка | Результат |
| --- | --- |
| Контрольна сума | **збігається**: `d1a000f8c465b496565b0f611ae6f65095086a8457c663f212ca5b17073fd7ef` |
| Розмір | 8 303 056 896 байт (7.7 GiB) |
| Формат | справжній ISO9660 (`CD001` за сектором 16) |
| Завантажувальні записи | **обидві прошивки**: El Torito з двома входами — x86 BIOS (4 сектори) і UEFI (5760 секторів) |
| Вміст | `/gnu/store/50vq55r36qcxh23czqxn7a7yajmbhlz49-wsm-live-tools-0.2.0/bin/wsm-install` |
| Завантаження в BIOS | **не перевірено** — у середовищі немає QEMU |
| Завантаження в UEFI | **не перевірено** — те саме |

Образ збирався з п'яти частин (`part001`…`part005`), склеєних у порядку. Після
склеювання хеш збігся з `ISO-CHECKSUMS.sha256` — тобто публікація не пошкодила
файл.

### Чого в образі немає

**Маркера `WSM_LIVE_READY`.** Пошук по всіх 8.3 ГБ не знайшов рядка ніде.

Причина не в збірці: профіль, з якого збирали (`systems/live-iso.scm`), не мав
служби маркера. Тобто критерій приймання **не міг** пройти на цьому образі — і
саме тому його ніхто не пред'явив.

Виправлено: маркер додано в `systems/live-iso.scm`, як він уже був у `live.scm`
і `live-minimal.scm`. Тест стежить, щоб жоден live-профіль не лишився без нього.

**Трьох інсталяторів.** У образі `wsm-install` без `--guided`, `--tui` і
`--check-env`, і без `wsm-install-agent`: він зібраний із коміту до цих змін.

`wsm-live-tools` копіює `wsm_install`, `wsm_hwcheck` і `schemas` з дерева
репозиторію під час збірки, тож наступна збірка з поточного `main` міститиме їх
автоматично.


### Що в образі насправді лежить

Прочитав усі 1944 унікальні елементи `/gnu/store` з образу:

| Пакет | Версія в образі |
| --- | --- |
| `plasma-desktop` | 6.5.5 |
| `sddm` | 0.21.0 |
| `network-manager` | 1.54.3 |
| `mesa` | 26.2.6 |
| `cups` | 2.4.14 |
| `bluez` | 5.79 |
| `pipewire` | 1.6.8 |
| **`pulseaudio`** | **17.0** |

Тобто робочий стіл усередині справді є: Plasma 6.5.5, SDDM, NetworkManager,
Mesa, CUPS, BlueZ. Це не порожній образ із правильною назвою.

**Але там два звукові стеки одночасно.** `pipewire-1.6.8` і `pulseaudio-17.0`
в одному store — це рівно той конфлікт, який я описав і прибрав у #262
(системний `pulseaudio-service-type` прибрано з `desktop.scm`, бо PipeWire у
home-конфігу обслуговує PulseAudio-протокол).

Образ зібрано до того виправлення, тож у ньому обидва демони. Наслідок на
практиці — боротьба за пристрій: спершу за володіння картою, потім за
Bluetooth-профілі, і виглядає це як «звук зник сам».

Це ще один аргумент, чому образ треба перезібрати з поточного `main`: у ньому
вже немає ні зайвого демона, ні відсутнього маркера, ні старого інсталятора.

### Що додає перевірка завантажувальних записів

Спершу я міг сказати лише «це валідний ISO9660». Це слабке твердження: файл із
правильним магічним числом може бути непридатний до завантаження.

Тепер `verify_live_release.py` читає каталог **El Torito** — структуру, яка
каже прошивці, що і звідки вантажити. В образі вона є, з двома входами:

```
validation: ok | platform id: x86 BIOS
default (BIOS): bootable=True media=0 sectors=4 load_lba=69623
section: platform=UEFI entries=1
   bootable=True sectors=5760 lba=4052787
```

Тобто образ **структурно здатний завантажитись і в BIOS, і в UEFI**. Це вже не
«сподіваємось, що завантажиться», а перевірений факт про сам файл.

Лишається те, чого структура не доводить: що ядро справді стартує, що воно
доходить до графіки й що маркер з'являється. Для цього потрібен QEMU.

### Чого цей запис не доводить

**Що образ завантажується.** Ніхто не запускав його в QEMU. Маркер, вміст і
формат — це різні рівні доказу, і тут є лише два з трьох.

**Що встановлення працює.** Інсталятор у образі не запускався.
