# ADR 0005: Контракт передінсталяційної перевірки та передачі backend-у

- Статус: **proposed — відкрите обговорення**
- Дата: 2026-11-25
- Пов'язане завдання: [#12](https://github.com/juv4uk/wsm-desktop/issues/12)
- Батьківський напрям: [#10](https://github.com/juv4uk/wsm-desktop/issues/10)
- Залежності: [#5 — hardware report schema](https://github.com/juv4uk/wsm-desktop/issues/5), [#6 — wsm-hwcheck](https://github.com/juv4uk/wsm-desktop/issues/6), [#7 — installer integration](https://github.com/juv4uk/wsm-desktop/issues/7)

## Мета

Визначити вузький, перевірюваний контракт між апаратною діагностикою WSM, інтерфейсом інсталятора та нативним системним backend-ом. Контракт має дозволити змінювати frontend або backend незалежно, не перетворюючи WSM на спробу уніфікувати внутрішні механізми NixOS і Guix System.

Цей ADR не обирає інсталятор і не визначає повну конфігурацію ОС. Він визначає порядок дій, межі довіри та умови, за яких дозволено перейти від read-only перевірки до потенційно руйнівної операції.

## Рішення, запропоноване до ратифікації

Потік інсталяції має п'ять окремих фаз:

1. **Preflight** — запустити локальний read-only collector та отримати версійований hardware evidence report.
2. **Interpretation** — перевірити схему, показати факти, джерела, час спостереження, невідомі стани та обмеження.
3. **Planning** — сформувати backend-specific план без запису на цільові диски.
4. **Confirmation** — показати точну ціль, наслідки та backend; отримати явне підтвердження користувача.
5. **Handoff** — повторно перевірити ціль і передати план рівно одному backend adapter-у.

Жоден frontend-компонент не має права самостійно обходити ці фази. Успішний preflight не є дозволом на запис.

## 1. Вхідні дані та довіра до звіту

Перший обов'язковий вхід — JSON report від `wsm-hwcheck`, що відповідає підтриманій версії [WSM Hardware Evidence Report v1](https://github.com/juv4uk/wsm-desktop/issues/5) та її JSON Schema.

Споживач повинен:

- перевірити JSON parse, schema version і повну валідацію проти відповідної схеми;
- відхилити відсутній, пошкоджений або непідтримуваний звіт із конкретним поясненням;
- перевірити, що звіт належить поточному запуску live-середовища, а не випадково підхоплений старий файл;
- зберігати походження кожного факту: collector/source, версію за наявності, timestamp і рівень впевненості;
- трактувати `unknown`, `not-run`, `not-detected` та відсутність необов'язкового джерела відповідно до їх семантики, а не зводити їх до `failed`.

Початковий контракт працює офлайн. Звіт v1 не потребує мережевого доступу, зовнішньої бази чи завантаження probe. Якщо майбутня версія додасть віддалене збагачення, воно буде окремою необов'язковою фазою з окремою згодою, описом переданих категорій даних та санітизованою копією. Воно не може бути прихованою передумовою інсталяції.

## 2. Інтерпретація апаратних доказів

Інтерфейс має розділяти щонайменше такі стани для кожного релевантного пристрою:

| Вимір | Що можна стверджувати |
| --- | --- |
| Виявлення | Пристрій виявлено, не виявлено або стан невідомий |
| Driver | Драйвер прив'язаний, модуль завантажений без binding, кандидат лише відомий, помилка або невідомо |
| Runtime firmware | Firmware завантажено, відсутнє, сталася помилка, не потрібне або невідомо |
| Функція | Конкретний тест пройшов, провалився, частково пройшов, не запускався, не підтримується або невідомо |

«Драйвер прив'язаний» не означає «пристрій функціонально перевірений». Наявність firmware-файлу не доводить, що ядро його завантажило. Виявлений EDID або advertised display mode не доводить, що GPU, порт, кабель і монітор стабільно працюють у цьому режимі.

WSM не повинен обчислювати єдиний непрозорий бал сумісності. Підсумок формується з конкретних доказів та зрозумілих наслідків для обраного сценарію інсталяції.

## 3. Правила рішень: hard stop проти попередження

Невідомий стан сам по собі не є несумісністю та не повинен автоматично блокувати інсталяцію.

Інсталятор може застосувати hard stop лише тоді, коли є конкретна, пояснювана умова, що робить наступну операцію неможливою або небезпечною. Приклади:

- не виявлено жодної допустимої цілі для встановлення;
- ціль не може бути однозначно ідентифікована або її стан змінився після побудови плану;
- неможливо підтвердити безпечну модель розмітки/монтування;
- звіт або план не пройшов валідацію;
- backend adapter не може гарантувати, що виконає саме підтверджений план.

Відсутність Wi-Fi, невідомий статус аудіо, відсутність зовнішнього запису про GPU чи неперевірений sleep/resume зазвичай є попередженням, а не забороною встановлення. Для мережевої інсталяції відсутність робочого мережевого шляху може стати hard stop саме цього сценарію, але користувачу треба пояснити альтернативу (наприклад, offline install), якщо вона підтримується.

Hard stop має посилатися на конкретні факти/перевірки та вказувати, що саме потрібно виправити. Не можна маскувати попередження під помилку або навпаки.

## 4. Backend-neutral intent і backend-specific plan

Спільний рівень може передавати намір користувача: locale, timezone, клавіатуру, профіль системи, обраний диск/розмітку, mount points, політику nonfree компонентів та ідентифікатор hardware report.

План після вибору backend-а стає **backend-specific**. Він повинен містити щонайменше:

- версію формату плану;
- backend ID: `guix` або `nix`;
- ID і версію hardware report, на якому базується рішення;
- нормалізовані параметри системи та розмітки;
- точну ціль інсталяції та очікуваний стан цілі;
- перелік операцій, які будуть виконані, і їхні наслідки;
- посилання на попередження, які користувач погодився прийняти;
- ідентифікатор/хеш підтвердженої версії плану.

План має бути серіалізований у JSON, придатний для перевірки та журналювання. Після підтвердження його зміна створює нову версію і вимагає нового підтвердження. Frontend не може непомітно підмінити backend, диск, розмітку чи профіль після підтвердження.

Спільний план не повинен намагатися кодувати довільні параметри NixOS module system або Guix operating-system declaration. Backend adapter відповідає за перетворення підтриманого intent у власну нативну конфігурацію та відмовляється від невідомих/непідтриманих полів, а не ігнорує їх мовчки.

## 5. Єдиний власник встановлення

Для однієї інсталяції вибирається рівно один backend:

- Guix plan передається тільки Guix adapter-у, який використовує штатний Guix deployment path;
- Nix plan передається тільки Nix/NixOS adapter-у, який використовує штатний NixOS deployment path.

Ніякого спільного запуску `guix system init` і `nixos-install` для одного root filesystem. Не можна дозволяти frontend-у та backend-у одночасно встановлювати bootloader або керувати тією самою системною конфігурацією. Власник bootloader, root filesystem, store, сервісів та активації визначається обраним backend-ом і явно відображається в плані.

Frontend передає структуровані аргументи через adapter API/argv, а не будує shell-команду конкатенацією рядків. Секрети (паролі, recovery keys) не зберігаються у звіті, JSON-плані, звичайних логах чи аргументах процесу; для них потрібен окремий захищений канал введення/передавання.

## 6. Повторна перевірка цілі та межа запису

Між побудовою плану та першим записом середовище може змінитися. Тому безпосередньо перед handoff adapter зобов'язаний:

1. повторно перевірити, що ціль існує та однозначно відповідає підтвердженій цілі;
2. звірити доступні стабільні атрибути (модель, розмір, bus/порт та інші безпечні ознаки) з очікуваним станом;
3. відхилити handoff, якщо пристрій зник, замінився, змінив розмір або ідентифікація стала неоднозначною;
4. перевірити незмінність підтвердженого плану;
5. ще раз перевірити, що запускається саме обраний backend.

Сирі серійні номери, WWN та інші чутливі ідентифікатори не додаються до hardware report. Якщо для захисту від підміни цілі потрібен системний ідентифікатор, його слід тримати у короткоживучому локальному контексті плану, показувати користувачу без розкриття секретних значень і не відправляти мережею.

Усі інтеграційні тести виконуються лише на disposable QEMU-дисках. Dry-run має завершитися до відкриття цільового блочного пристрою для запису. Цей ADR не дозволяє фізичну інсталяцію як частину прототипування.

## 7. Мінімальний життєвий цикл

Рекомендовані стани:

`not-started → report-ready → report-validated → plan-draft → plan-confirmed → handoff-started → completed`

З будь-якого стану до початку запису можна перейти в `aborted`. Помилка валідації, зміна цілі або відмова користувача не повинні переходити у handoff.

Після початку запису скасування не можна називати rollback, якщо backend не підтверджує, що система повернута до попереднього стану. Журнал має фіксувати останню завершену фазу та точну причину зупинки.

## 8. Acceptance assertions

Контракт вважається реалізованим лише якщо автоматизовані тести доводять такі твердження:

1. Відсутній report → немає disk plan і немає disk write.
2. Некоректний JSON → зрозуміла помилка, немає handoff.
3. Непідтримувана major schema version → відмова без спроби «вгадати» формат.
4. Невідомий статус пристрою → UI показує «невідомо», а не «несумісно».
5. Відсутність необов'язкового remote source → offline preflight продовжується.
6. Кожне попередження має джерело/час або явну позначку, що вони невідомі.
7. Hard stop має конкретний machine-checkable reason code та пояснення.
8. Зміна backend після підтвердження → підтвердження анулюється.
9. Зміна цільового диска/його атрибутів після підтвердження → handoff відхиляється.
10. Зміна будь-якого поля підтвердженого плану → потрібне повторне підтвердження.
11. Guix plan викликає тільки Guix adapter; Nix plan — тільки Nix adapter.
12. Dry-run не відкриває цільові диски для запису і не змінює bootloader/EFI.
13. Невдала валідація або abort не запускає backend installer.
14. Секрети відсутні у звіті, плані та звичайних логах.
15. QEMU smoke test підтверджує послідовність preflight → plan → confirmation → backend handoff на одноразовому диску.

Тести мають перевіряти не лише повідомлення UI, а й відсутність викликів backend та відсутність операцій запису.

## Наслідки

Переваги:

- апаратна діагностика залишається незалежною від frontend та backend;
- frontend можна змінити без переписування collector-а;
- однаковий користувацький намір може бути реалізований окремими нативними backend-ами;
- небезпечні переходи стають тестованими й аудитовними;
- невідомі докази не перетворюються на хибні заяви про несумісність.

Витрати та обмеження:

- потрібні окремі backend adapters і їхні інтеграційні тести;
- план потребує версіонування та повторної перевірки цілі;
- деякі апаратні функції неможливо надійно перевірити до встановлення;
- універсальність обмежується спільним intent; специфічні функції backend-ів не перекладаються автоматично.

## Що не вирішує цей ADR

- вибір Calamares, archinstall чи іншого frontend-а;
- повний JSON Schema для install plan;
- реалізація collector-а або його апаратних тестів;
- вибір primary backend для першого preview;
- дозвіл на встановлення на фізичне обладнання.

Ці питання залишаються в межах пов'язаних задач і окремих рішень. Ратифікація цього ADR потребує review від власників hardware report/collector та backend прототипів.
