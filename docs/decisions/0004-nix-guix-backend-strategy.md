# ADR 0004: Nix і GNU Guix як окремі кандидати на системну основу WSM

<!-- SPDX-License-Identifier: CC-BY-SA-4.0 -->

- Статус: **proposed — відкрите архітектурне обговорення**
- Дата: 2026-11-25
- Пов'язане завдання: [#2](https://github.com/juv4uk/wsm-desktop/issues/2)

## Контекст

Початковий план WSM Desktop використовував GNU Guix System як єдину системну основу. Під час локальної роботи з'ясувалося, що середовище розробника вже має Nix, і локальний агент почав використовувати його для експериментів.

Це відкриває ширший напрямок: WSM може досліджувати Nix та GNU Guix як дві сильні декларативні системи, але створювати власний спільний продукт, а не форкати одну з них або намагатися механічно злити їхні внутрішні механізми.

## Важливе розмежування понять

- **Nix** — пакетний менеджер і мова/модель опису збірок.
- **NixOS** — операційна система, що використовує Nix для побудови системних конфігурацій і керує їх активацією.
- **GNU Guix** — функціональний пакетний менеджер.
- **Guix System** — операційна система з декларативною конфігурацією, побудованою на Guix.

Тому порівнюємо не лише дві мови рецептів, а дві повні моделі побудови, активації, обслуговування та відновлення Linux-систем.

## Пропоноване рішення

Розділити WSM на спільний продуктний рівень та окремі нативні backend-и.

### 1. Спільний рівень WSM

Власна робота WSM зосереджується на можливостях, які користувач має отримувати незалежно від backend-а:

- графічна інсталяція та зрозумілий сценарій першого запуску;
- нейтральний опис апаратного забезпечення та доказів сумісності;
- зрозумілі профілі Desktop, Developer та Hardware Compatibility;
- перевірка конфігурації до незворотних операцій;
- контрольовані оновлення, перевірка працездатності та відновлення;
- походження пакетів, ліцензії, довіра до підписів та build manifests;
- інтерфейс налаштування системи без вимоги знати Nix або Guile Scheme.

### 2. Нативні backend-и

На етапі дослідження допускаються два незалежні прототипи:

- **WSM Nix backend** — нативний Nix/NixOS шлях;
- **WSM Guix backend** — нативний Guix System шлях.

Backend відповідає за власну мову декларацій, пакетні джерела, сервісний менеджер, побудову та активацію системи. WSM не намагається автоматично перетворювати довільні Nix expressions на Guix Scheme чи навпаки.

### 3. Спільний контракт, але не універсальний опис усієї ОС

Можна визначити невелику backend-neutral схему для таких даних:

- мова, locale, timezone, клавіатура;
- апаратна інвентаризація та вимоги до драйверів/firmware;
- користувацькі наміри щодо програмних профілів;
- план розмітки диска та mount points;
- політика оновлення, перевірки та відновлення.

Схема описує намір користувача та факти про обладнання. Вона не повинна намагатися представити кожен параметр NixOS module system або Guix operating-system declaration. Backend перетворює лише підтриману частину контракту у власну нативну конфігурацію, а специфічні можливості залишаються backend-specific.

## Жорстка межа: один власник установленої системи

Для першої архітектури не зливати Nix і Guix у спільний runtime:

- не об'єднувати `/nix/store` та `/gnu/store`;
- не намагатися імпортувати derivations як взаємозамінні артефакти;
- не дозволяти двом daemon-ам керувати однією системною конфігурацією;
- не запускати два механізми активації для одного root filesystem;
- не дозволяти двом backend-ам незалежно керувати bootloader або системними службами.

Одна інсталяція WSM повинна мати один системний backend та одну точку істини для bootloader, root filesystem, системних служб, generations і системних оновлень.

Технічне співіснування Nix і Guix як окремих інструментів у спеціальних developer environments можна досліджувати, але воно не є основою першого інсталяційного образу.

## Що означає «позбутися проблем»

WSM не обіцяє усунути всі обмеження upstream. Кожну проблему потрібно перетворити на спостережуваний дефект, сценарій та критерій приймання.

| Напрямок | Що потрібно перевіряти та покращувати |
| --- | --- |
| Відтворюваність | Зафіксовані revisions, хеші джерел, lock/manifests, повторювані CI builds |
| Довіра | Перевірка підписів каналів і кешів; жодних неявних signing keys чи невідомих binary caches |
| Оновлення | Нова конфігурація спочатку будується та перевіряється; невдала активація має безпечний шлях відновлення |
| Rollback | Старі покоління зберігаються за прозорою retention policy; очищення не повинно непомітно руйнувати можливість відкату |
| Дисковий простір | Вимірюваний облік stores, generations і cache; GC із попередженням та зрозумілим впливом |
| Апаратна підтримка | Матриця доказів по конкретних моделях, драйверах, firmware, kernel і версіях; не просто загальна позначка «підтримується Linux» |
| UX | Один зрозумілий сценарій встановлення та управління; складність backend-а не перекладається на користувача |
| Пакети | Видимий статус доступності substitute/build, пояснення помилок і походження кожного компонента |
| Сумісність | Кожна підтримувана конфігурація тестується у VM та на конкретному обладнанні |

Ці критерії — цілі дослідження, а не твердження, що обидва upstream мають однакові дефекти.

## Факти, які вже впливають на дизайн

### Nix/NixOS

- NixOS будує системні конфігурації з декларацій, а нові покоління дозволяють повернутися до попереднього стану.
- Nix зберігає пакети у власному store; старі системні покоління та їхні замикання можуть залишатися на диску до очищення.
- Офіційна документація nix.dev досі описує flakes як експериментальний формат із відкритими проблемами. Це не означає, що весь Nix або NixOS є експериментальним.
- Для NixOS 26.05 документація вже описує можливість завантажувати конфігурацію з `system.nix`, тому WSM не повинен ототожнювати NixOS із вимогою використовувати flakes для кожної системи.

### GNU Guix

- Guix використовує окремий store і daemon, а системні конфігурації описуються Scheme.
- Guix має механізм автентифікації каналів за введенням каналу та підписами уповноважених розробників.
- Substitute servers пришвидшують встановлення, але користувач має розуміти, які ключі авторизовані та які саме артефакти доступні.
- Вільний системний профіль і сторонній nonfree канал мають залишатися явно розділеними.

### Calamares

Calamares більше не базовий кандидат на frontend: напрямок hardware-first frontend запропоновано в [PR #100 / ADR 0006](https://github.com/juv4uk/wsm-desktop/pull/100). Він не вирішує backend deployment самостійно: WSM повинен мати окремі Nix/NixOS та Guix deployment adapters або один adapter лише для обраного backend-а.

### Статус доказової бази (2026-11-25)

- Gate [#55](https://github.com/juv4uk/wsm-desktop/issues/55) вимагає реального boot-доказу, а не лише успішної збірки. Пакет доказів для Guix-шляху опубліковано в [#1](https://github.com/juv4uk/wsm-desktop/issues/1#issuecomment-7172142987): точний SHA, версії, exit codes, реальну ревізію каналу, `guix system build`, `guix system vm`, serial-маркер `wsm-desktop login:` з `vm_exit=0`, розкриття TCG і disposable-образи.
- Окремого еквівалентного real-boot пакета для Nix/NixOS поки немає; тому цей ADR лишається `proposed`, а вибір primary backend-а в #2 не ратифіковано.
- `--full-boot` через GRUB у TCG до ядра не дійшов і як успішний boot не заявляється.

## Експериментальний план

1. Зберегти поточну локальну роботу та логи без перезапису.
2. Зафіксувати реальне середовище Nix: версія, канали/flake inputs, спосіб побудови, VM launch і обмеження.
3. Окремо побудувати мінімальну Guix System у disposable QEMU VM.
4. Порівняти однакові критерії: installation, boot, updates, rollback, store growth, package availability, hardware path, developer UX.
5. Створити problem register із пріоритетами та acceptance tests.
6. Вибрати один з напрямків:
   - один primary backend для першого WSM Desktop preview;
   - дві незалежні редакції WSM, якщо обидві доведені та супроводжувані.

## Тимчасова рекомендація

Поки що не обирати переможця. Продовжити Nix-експеримент, не викидати Guix-конфігурацію, а перший публічний preview планувати тільки після доказу, що хоча б один backend дає цілісну систему.

Перевагу двом незалежним backend-ам можна надати лише тоді, коли спільний UX не змушує WSM дублювати або приховувати системні механізми.
