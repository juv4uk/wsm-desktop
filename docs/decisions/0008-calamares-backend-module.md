# ADR 0008: Calamares як frontend, WSM як jobmodule

<!-- SPDX-License-Identifier: LicenseRef-Volnist -->

- Статус: **proposed — потребує ратифікації в [#10](https://github.com/juv4uk/wsm-desktop/issues/10)**
- Дата: 2026-11-26
- Переглядає: [ADR 0006](0006-hardware-first-installer-frontend.md) (власний frontend за формою archinstall)
- Повертає до розгляду: [ADR 0002](0002-calamares-as-installer.md)

## Контекст

ADR 0006 пропонував власний hardware-first frontend, аргументуючи це тим, що
Calamares тісно пов'язаний зі своїм payload і bootloader-ом, а archinstall дає
найпридатнішу форму взаємодії.

Цей аргумент виглядав переконливо, доки не з'явився контрприклад.

## Контрприклад: NixOS

NixOS — найближчий родич Guix: та сама декларативна модель, ті самі покоління
й відкат, та сама відсутність класичного пакетного менеджера. І NixOS
**постачає графічний інсталятор на Calamares**:

- `nixos/modules/installer/cd-dvd/installation-cd-graphical-calamares.nix`
  підключає `calamares-nixos`, `calamares-nixos-extensions` і autostart;
- Calamares викликає `nixos-generate-config` і збирає систему в цільовий диск;
- екран «Partitioning» показує, чи інсталятор завантажився в BIOS чи UEFI —
  рівно та перевірка, яку ми описали в прийманні образу.

Тобто «Calamares прив'язаний до payload» — хибне узагальнення. Він прив'язаний
до **модулів**, а модулі пише той, хто ставить систему. NixOS написав свої й
працює.

## Рішення

Використовувати Calamares як frontend, а WSM — як jobmodule.

Що це означає конкретно:

| Шар | Хто робить |
| --- | --- |
| Мова, локація, клавіатура, користувач | Calamares, з коробки |
| Розбиття диска | Calamares (kpmcore), з нашим підтвердженням цілі |
| Перевірка заліза й докази | **WSM**: `wsm-hwcheck`, gate доказів, матчер профілю |
| Вибір профілю | **WSM**: Desktop / Compatibility |
| Запис системи | **WSM**: `guix system init` із нашими кроками |

Наші напрацювання — розбиття, послідовність кроків, gate доказів, матчер
профілю — стають **бекендом модуля**, а не власним UI. Це не втрата роботи: це
та сама робота, але без написання тисяч рядків Qt.

## Наслідки

**Позитивні:**

- не пишемо UI, локалізацію, екран розбиття й обробку помилок з нуля;
- отримуємо перевірені сценарії (erase disk, LUKS, BIOS/UEFI) безкоштовно;
- збіг із тим, як це робить єдиний проєкт з такою ж архітектурою.

**Негативні:**

- залежність від Qt/KDE-стеку в live-образі (у нас Plasma все одно є);
- Calamares — C++/Qt, і його jobmodules — Python: наш код має пройти через їхній
  інтерфейс;
- оновлення Calamares може зламати модуль; потрібна перевірка на кожній
  фіксованій ревізії.

## Що це не вирішує

- **Не ратифікує рішення.** Це пропозиція; рішення в #10.
- **Не скасовує наші модулі.** `partition.py` та `install_steps.py` лишаються:
  вони і є те, що викликає jobmodule.
- **Не вирішує Secure Boot.** NixOS вимагає вимкнути його для завантаження
  інсталятора; у нас та сама ситуація, і це окреме завдання.

## Альтернативи, які розглянуто

| Варіант | Чому ні |
| --- | --- |
| Власний frontend за формою archinstall (ADR 0006) | UI, локалізація, розбиття й обробка помилок — місяці роботи, яку NixOS уже зробив інакше |
| Anaconda (Fedora) | прив'язаний до RPM і своїх модулів, важчий за Calamares |
| YaST / libhd (openSUSE) | найсильніше виявлення заліза, але тісно пов'язаний зі своїм payload |
| Тільки CLI (`wsm-install`) | залишається як шлях для досвідчених; не може бути єдиним входом для десктопа |
