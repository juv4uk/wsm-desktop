# Докази для профілю заліза

<!-- SPDX-License-Identifier: LicenseRef-Volnist -->

- Статус: **формат реалізовано**, жодного реального профілю ще не заведено
- Задачі: [#171](https://github.com/juv4uk/wsm-desktop/issues/171) (профілі H170), [#8](https://github.com/juv4uk/wsm-desktop/issues/8) (матриця сумісності)
- Схема: [`schemas/profile-evidence.schema.json`](../schemas/profile-evidence.schema.json)
- Перевірка: `make check-profile-evidence` або `python3 scripts/check_profile_evidence.py`

## Версійність

Контракт `/2` є несумісною зміною початкового `/1`: він вимагає явного ISA level, відносний POSIX path і SHA-256 для кожного артефакту, а також може містити `hardware_signature` для автоматичного зіставлення з апаратним звітом. Реальних `/1` bundle-споживачів у репозиторії не було; старі записи не можна мовчки трактувати як `/2`.

## Різниця, яку фіксує цей формат

Є два способи сказати «ця машина підтримується»:

1. «Ми написали конфігурацію для H170, має працювати.»
2. «Ми перевірили конкретну машину в конкретному середовищі, ось звіт `wsm-hwcheck`, ось що працює, ось що ні, ось що ми не перевіряли.»

Перше — гіпотеза. Друге — доказ. Формат нижче існує, щоб друге було дешевшим за перше.

## Обов'язкові поля

| Поле | Навіщо |
| --- | --- |
| `report_id`, `report_schema_version` | точне посилання на звіт, із якого взято докази |
| `isa_level` | рівень із контракту `wsm-cpu-isa/1`; якщо його неможливо підтвердити, явно `unknown` |
| `verified_functions` | функції зі статусом `pass`, `fail` або `not-assessed` |
| `known_limitations` | усі відомі несправності та часткові обмеження |
| `not_assessed` | **непорожній** перелік того, що не перевірено |
| `artifacts` | **непорожній** перелік файлів-доказів із locator і SHA-256 |

У кожному елементі `artifacts` обов'язкові `kind`, `path` і `sha256`. Шлях — безпечний відносний POSIX-шлях від теки профілю, наприклад `artifacts/dmesg.txt`. Сам файл має зберігатися поруч із `evidence.json` у цій теці. Валідатор відхиляє абсолютні шляхи, `..`, symlink-шляхи, відсутні файли та невідповідність SHA-256. Тому digest прив'язаний до конкретних байтів, які реально можна перевірити.

## Правила, які перевіряються

JSON Schema перевіряє форму, а скрипт — зв'язки з файловою системою та семантику:

- **хоча б одна функція має `pass`** — bundle, де все `not-assessed`, нічого не доводить;
- **кожен `fail` має бути в `known_limitations`** — інакше профіль читається як здоровий, поки він хворий;
- **`verified_by` — лише неперсональна роль** з allowlist: `автори проєкту`, `local agent` або `web agent`;
- **`slug` збігається з текою** `<vendor>/<model>`;
- **кожен артефакт існує і має заявлений SHA-256**;
- **кожен `profile.scm` має відповідний `evidence.json`**, а orphan evidence bundle без профілю теж відхиляється.

## Чому `not_assessed` не може бути порожнім

Порожній список означає «ми перевірили все», а це майже завжди неправда: suspend/resume, HDMI-звук, Bluetooth-профілі, поведінка після трьох годин роботи — щось та лишається.

Краще чесно перелічити п'ять неперевірених речей, ніж отримати користувача, який вважав профіль гарантією.

## Запуск і коди завершення

```sh
make check-profile-evidence
# або для окремої нестандартної теки:
python3 scripts/check_profile_evidence.py --dir /path/to/hardware-profiles
# окремий файл: перевіряється schema та SHA-256 артефактів, але не slug теки
python3 scripts/check_profile_evidence.py --file /path/to/evidence.json
```

- Порожній корінь без жодного `profile.scm` та bundle — успішний стан «профілів ще немає».
- Виявлений `profile.scm` без `evidence.json`, evidence без парного профілю або невалідний bundle — код завершення `1`.
- Неіснуючий каталог/файл — код завершення `2`.

Перевірка каталогу виконується відносно саме переданого `--dir`, а не шляху репозиторію за замовчуванням.

## Зв'язок з інсталятором

Правило проєкту: **профіль без валідного `evidence.json` не може бути допущений до інсталяції**. Цей скрипт і `make check` забезпечують перевірку контракту в репозиторії/CI. Інтеграція цього gate у runtime інсталятора ще не реалізована; не трактувати сам факт успішного `make check-profile-evidence` як доказ, що інсталятор уже відхиляє непідтверджені профілі.

## Як інсталятор знаходить профіль

Профіль оголошує `hardware_signature` — набір пар `vendor:device`, за якими
машину можна впізнати:

```json
"hardware_signature": {"pci_ids": ["10de:1c82", "8086:a170"], "match": "all"}
```

`wsm_install/profile_match.py` порівнює їх з тим, що є у звіті `wsm-hwcheck`.

Правила навмисно строгі:

- **`match: all`** (типово) — потрібні всі пари; частковий збіг не рахується;
- **`match: any`** — досить однієї;
- **профіль без підпису не матчиться автоматично** — його можна застосувати
  руками, але інсталятор не заявлятиме, що він підходить;
- **два профілі на одну машину — це неоднозначність**, а не привід обрати
  перший.

Вгадувати тут означало б знищити сенс доказів: неправильний профіль гірший за
відсутній, бо він **виглядає** перевіреним.

## Чого тут ще немає

- **Жодного реального профілю.** Формат є, наповнення — робота власника (#171) на реальній машині. Вигадувати докази не можна.
- **Зв'язку з інсталятором у коді.** Runtime enforcement залишається окремою задачею.
- **Перевірки, що `report_id` справді існує** в сховищі звітів. Сховища звітів поки немає.
