# Розділення привілеїв

- Статус: **preview-only; APPLY вимкнено незалежно від UID**
- Код: [`wsm_install/agent.py`](../wsm_install/agent.py)
- Тести: `tests/test_agent.py` (22)

## Проблема

До цього весь інсталятор працював від root: інтерфейс, планувальник і
виконавець. Отже будь-яка помилка в обробці аргументів — це помилка з правами
root.

Так само це вирішує elementary installer: UI працює від користувача, а демон
`io.elementary.installer-daemon` від root виконує руйнівні операції.

## Як зроблено тут

Це лише прототип межі, а не готовий привілейований сервіс:

1. Непривілейована частина будує план і **пише його у файл**
   (`--write-plan plan.json`).
2. `wsm-install-agent --plan plan.json --dry-run` читає JSON, перевіряє
   схему, типи й allowlist та передає кроки до спільного preview-only executor.
3. Будь-який запуск без `--dry-run` відхиляється з
   `agent.apply-disabled` **до executor і subprocess**, незалежно від того,
   запущений процес від root чи звичайного користувача.

Перелік `ALLOWED_PROGRAMS` наразі є лише кандидатом для майбутнього
обмеженого протоколу. Він не надає дозволу запускати ці програми.

## Що агент відхиляє

| Відмова | Код | Чому це важливо |
| --- | --- | --- |
| програма поза allowlist | `agent.not-allowed` | скомпрометований UI не може запустити `sh -c` через інсталятор |
| голе ім'я програми | `agent.not-allowed` | пошук у `PATH` від root — помилка Omarchy #8172 |
| метасимвол оболонки в аргументі | `agent.shell-metacharacter` | виконавець не використовує shell, але майбутній рефакторинг не має відкрити ці двері |
| план не за схемою | `agent.bad-schema` | зламаний план падає до першого диска, а не посередині |
| більше 32 кроків | `agent.too-many-steps` | план — це сім кроків; тридцять два означає, що щось не так |
| будь-який реальний запуск | `agent.apply-disabled` | root сам по собі не доводить target identity, згоду чи безпечний postcondition |

## Allowlist

Рівно те, що потрібно інсталятору, з абсолютними шляхами:

```
/usr/sbin/partprobe   /usr/bin/udevadm    /usr/sbin/mkfs.ext4
/usr/sbin/mkfs.btrfs  /usr/sbin/mkfs.xfs  /usr/sbin/mkfs.fat
/usr/bin/mount        /usr/bin/mkdir
```

Нічого більше. Не `dd`, не `sh`, не `guix` — передача системи в Guix
відбувається окремим кроком, який агент не виконує.

## Чого агент не робить

**Не є пісочницею й зараз не пише на диск.** Агент лише перевіряє та показує план; реальний APPLY вимкнено.

**Не автентифікує автора плану.** JSON-файл не підписаний і не прив'язаний до
процесу, що його створив. Тому його не можна вважати авторизованим для запису.

**Не виконує `guix system init`.** Це окремий крок, і він свідомо поза
allowlist: навіть запис на диск наразі не дозволено.

## Чого ще немає

- **Незалежної перевірки identity диска** (major/minor, розмір, топологія,
  removable/system-disk status) безпосередньо перед будь-яким записом.
- **Digest-bound consent** для кожної destructive operation, включно з
  повторним підтвердженням після зміни target або command plan.
- **Автентичності плану** та захищеного каналу між UI і майбутнім daemon.
- **Перевіреної tool closure** із Guix live environment; абсолютний шлях сам
  по собі не доводить наявність і довіру до виконуваного файлу.
- **Реальних postconditions, recovery та interruption tests.**
- **Журналу дій агента** окремо від stderr.
- **Destructive acceptance** лише на disposable QEMU scratch disk; фізичний диск
  не використовувався.
