# Архітектура WSM Desktop

<!-- SPDX-License-Identifier: LicenseRef-Volnist -->

## Мета

WSM Desktop — незалежний hardware-oriented настільний дистрибутив. Для першого підтримуваного preview обрано GNU Guix System як єдиний системний backend за ADR 0004. Nix/NixOS залишається окремим відкладеним дослідницьким напрямом і не входить до CLI, plan або release contract v0.1.

Ми не переписуємо пакетний менеджер, init system, ядро, драйвери або firmware заради самого факту власної розробки. Власна робота зосереджується на апаратній базі знань, перевірці сумісності, інтеграції upstream-компонентів, профілях системи, досвіді встановлення та документації.

## Компоненти

### GNU Guix System

Guix відповідає за:
- опис цільової операційної системи мовою Scheme;
- пакети, служби, облікові записи та системні налаштування;
- керування поколіннями системи;
- розгортання цільової файлової системи через штатні системні команди.

Конфігурація має бути декларативною та придатною до рев'ю. Випускні збірки повинні фіксувати ревізії каналів і записувати використані джерела.

### Installer frontend (candidate: Calamares)

Calamares був початковим кандидатом для графічної інсталяції, але більше не вважається обраним frontend-ом. Напрямок #10 оцінює його разом з іншими варіантами та власною тонкою оболонкою WSM.

Будь-який обраний frontend має забезпечити:
- зрозумілий guided workflow;
- мову, клавіатуру та часовий пояс;
- показ hardware preflight до вибору/підтвердження target disk plan;
- review плану перед незворотними діями;
- повідомлення про помилки та журнал інсталяції.

Frontend не є механізмом декларативного керування Guix або NixOS. Він потребує WSM adapter-а до одного обраного native backend-а.

### WSM Guix deployment adapter

Адаптер — власна інтеграційна межа між обраним installer frontend та Guix. Якщо frontend-ом стане Calamares, цей adapter інтегрується з його job/module API. Його майбутні обов'язки:

1. Отримати структуровані дані інсталяційного плану.
2. Перевірити їх типи, повноту та взаємну узгодженість.
3. Перевірити змонтовану цільову файлову систему та EFI System Partition.
4. Згенерувати Guix System configuration без виконання користувацького Scheme-коду.
5. Перевірити конфігурацію командою Guix до запису цільової системи.
6. Запустити штатне розгортання Guix із контрольованим журналюванням.
7. Передати Calamares зрозумілий результат або помилку.

Адаптер не повинен збирати shell-команду шляхом конкатенації довільних даних з UI. Значення користувача мають проходити allow-list/типову перевірку та потрапляти у конфігурацію через безпечне кодування.

## Потік встановлення

    Live system
        -> selected installer frontend
        -> partitioning and mounting
        -> WSM configuration / preflight
        -> generated Guix System configuration
        -> guix system build
        -> guix system init
        -> post-install validation

Це цільова архітектура. Вона ще не реалізована наскрізно.

## Власність компонентів

| Відповідальність | Власник |
| --- | --- |
| Пакети та системні служби | GNU Guix |
| Nonfree package definitions (коли ввімкнено) | Nonguix та відповідні upstream |
| UI і навігація інсталятора | Calamares |
| Інсталяційна політика WSM | WSM Desktop |
| Генерація Guix-конфігурації | WSM Desktop |
| Тестові профілі обладнання | WSM Desktop, з джерелами доказів |

## Bootloader — одна точка відповідальності

Guix System configuration описує bootloader. Штатна команда guix system init встановлює завантажувач, визначений цією конфігурацією, якщо не використано відповідний режим без встановлення bootloader.

Якщо WSM обере Calamares, не можна одночасно запускати його stock bootloader job та просити Guix встановлювати той самий завантажувач. Конкретний порядок перевіряється в інтеграційному тесті.

## User accounts — декларативна модель

Якщо WSM обере Calamares, його generic users module не вважається сумісним із Guix System без перевірки. WSM має сформувати user-account declarations у Scheme-конфігурації, передати хеш пароля безпечним шляхом і перевірити права на домашній каталог. Пароль у відкритому вигляді не можна писати в логи або коміти.

## Безпечна розробка

Перші тести виконуються на одноразових qcow2-образах у QEMU. Фізичні диски не є середовищем розробки. Перед будь-якою операцією запису адаптер повинен мати однозначний план і явне підтвердження користувача.


## Системний backend першого preview

GNU Guix System є єдиним обраним backend-ом першого WSM Desktop preview. CLI приймає лише `--backend guix`, а plan v0.1 емітує лише `guix-system`. Nix/NixOS збережено як відкладене дослідження в окремому середовищі; це не допустимий alias, план або залежність продуктового preview.

Спільний рівень WSM має містити UX, hardware inventory, compatibility evidence, профілі користувача, безпечні інсталяційні плани та політику оновлення. Він не повинен намагатися переписати повну семантику NixOS module system або Guix operating-system declaration в універсальну мову.

Одна конкретна інсталяція має одного системного власника. Не допускається паралельне керування тим самим root filesystem, bootloader, системними службами чи activation state двома backend-ами.

Рішення про Guix як перший і єдиний backend прийнято в [ADR 0004](decisions/0004-nix-guix-backend-strategy.md) та відображено в [issue #2](https://github.com/juv4uk/wsm-desktop/issues/2). Майбутнє reconsideration Nix/NixOS потребуватиме окремого рішення, власної перевірки й версійованого handoff contract; воно не може мовчки з'явитися в CLI або plan v0.1.

## Hardware-first та upstream-first

Апаратна сумісність — фундаментальна відповідальність WSM, а не необов'язковий екран інсталятора.

### Що повторно використовуємо

- upstream Linux kernel та готові kernel packages/configurations;
- upstream drivers, firmware packages та їхні підтримувані механізми доставки;
- hardware inventory, modalias, driver database, EDID/DisplayID, firmware та діагностичні інструменти;
- реальні hardware reports і тести спільноти — із датою, версією ядра, точним device ID та ліцензійним походженням.

### Що створює WSM

- версіонований нейтральний формат апаратного звіту;
- нормалізацію та зіставлення фактів з різних upstream-джерел;
- профілі конкретних пристроїв і конфігурацій із посиланнями на докази;
- правила вибору kernel/driver/firmware package для відповідного backend-а;
- pre-install compatibility preflight та зрозумілий звіт користувачу;
- автоматизовані тести, які відділяють discovery, driver binding, runtime firmware loading і функціональну перевірку.

### Політика збірок

WSM не повинна повторно компілювати upstream-компонент без причини. Порядок переваги:

1. придатний, сумісний і перевірений upstream package/artifact із довіреного джерела;
2. upstream recipe/derivation з відтворюваними inputs і перевіреним substitute/build artifact;
3. власна збірка з upstream source лише коли немає придатного artifact, потрібне цільове kernel configuration або потрібна контрольована інтеграційна зміна;
4. власний patch/fork — лише коли проблему не можна розв'язати конфігурацією чи upstream-виправленням; patch має бути задокументований і, де можливо, надісланий upstream.

Довірений substitute не стає довіреним лише тому, що він швидкий: source revision, підписи, ключі та provenance перевіряються окремо. WSM не додає сторонні caches або ключі непомітно.

### Evidence policy

Наявність hardware ID, модуля або запису у зовнішній базі не є доказом повної працездатності. Кожен профіль окремо відображає:
- пристрій виявлено;
- драйвер-кандидат відомий;
- драйвер реально прив'язаний;
- runtime firmware завантажено або зафіксовано помилку;
- конкретну функцію перевірено;
- даних недостатньо.

`unknown` та `not-tested` не можна перетворювати на `failed` або `supported` без доказів. Відсутність запису у базі не доводить несумісність.

Початковий технічний напрямок реалізується в [hardware preflight issues](https://github.com/juv4uk/wsm-desktop/issues/3) та [draft PR #9](https://github.com/juv4uk/wsm-desktop/pull/9).
