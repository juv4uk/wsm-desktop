## 1. Призначення та межі

Цей контракт визначає безпечний перехід від апаратних спостережень live-середовища до плану встановлення WSM Desktop. Він не обирає переможця між NixOS і Guix System, не описує повну схему конфігурації жодної з цих систем і не реалізує запис на диск.

WSM має повторно використовувати результати <code>wsm-hwcheck</code>, а не створювати другий детектор усередині інсталятора. Спільний рівень WSM відповідає за перевірку формату звіту, пояснення фактів, оцінку передумов, перегляд плану та підтвердження користувача. Нативний backend відповідає за власну конфігурацію і розгортання.

**Одна інсталяція — один системний backend.** Для першої версії підтримуються окремі шляхи <code>guix-system</code> або <code>nixos</code>. Їхні stores, декларації, activation-механізми та власність bootloader не змішуються.

Цей документ є контрактною пропозицією. Наявність документа не означає, що <code>wsm-install</code>, будь-який deployment adapter чи підтримуваний інсталяційний образ уже реалізовані.

## 2. Терміни та джерела істини

| Термін | Значення |
| --- | --- |
| Hardware report | Локальний JSON-звіт, створений збирачем за версіонованою схемою #5 |
| Raw fact | Спостереження з джерелом, часом і класом доказу; не інтерпретація інсталятора |
| Readiness assessment | Похідна оцінка передумов саме для вибраного сценарію встановлення |
| Install plan | Перевірюваний, backend-specific опис наміру користувача; сам по собі не виконує операцій |
| Confirmation | Явне погодження користувача з точними байтами плану та цільовим пристроєм |
| Deployment | Єдиний нативний шлях розгортання обраного backend-а |

Джерела істини не підміняють одне одного:

- схема #5 визначає допустиму структуру та значення звіту;
- <code>wsm-hwcheck</code> #6 збирає локальні спостереження;
- цей контракт визначає порядок перевірки та handoff;
- обраний backend визначає нативну конфігурацію та розгортання;
- GitHub issue/PR і CI є доказом фактичного стану реалізації. Цей документ не оголошує незлиті пропозиції реалізованими.

У звіті v1.0.0 немає поля «система сумісна» або універсального compatibility score. Інсталятор не повинен додавати таку семантику в звіт заднім числом. Readiness assessment зберігається окремо від raw facts і пояснює кожен висновок посиланням на докази.

## 3. Обов'язкова послідовність

~~~text
LIVE SESSION
    |
    v
COLLECT (wsm-hwcheck, read-only)
    |
    v
VALIDATE (JSON + supported schema)
    |
    v
ASSESS (critical prerequisites + alternatives)
    |
    v
SHOW EVIDENCE (facts, unknowns, warnings)
    |
    v
DRAFT BACKEND-SPECIFIC PLAN
    |
    v
REVIEW EXACT PLAN + TARGET
    |
    v
EXPLICIT CONFIRMATION OF PLAN DIGEST
    |
    v
REVALIDATE REPORT + TARGET TOPOLOGY
    |
    v
ONE NATIVE BACKEND DEPLOYMENT
    |
    v
POST-INSTALL VALIDATION
~~~

Жоден наступний крок не може мовчки пропустити попередній. Зокрема, інсталятор не показує план розмітки/запису, доки звіт не пройшов перевірку і не вирішені критичні невідомості для конкретного сценарію.

### 3.1. Збір

1. Збір виконується в live-середовищі до будь-якої операції запису на цільовий диск.
2. Інсталятор запускає наявний <code>wsm-hwcheck</code> у read-only режимі або читає створений ним звіт. Інсталятор не дублює PCI/USB/sysfs/DRM-інвентаризацію.
3. Збір за замовчуванням локальний та офлайн. Він не надсилає probe, не робить зовнішніх lookup-запитів, не встановлює пакети, не завантажує модулі й не оновлює firmware.
4. Відсутня утиліта, заборонений доступ або неповний sysfs/procfs не є підставою вигадувати значення. Факт залишається <code>unknown</code> або <code>not-tested</code> із поясненням.
5. Режим запуску та точний час збору зберігаються у звіті. За зміни апаратного складу або повторного завантаження live-сесії звіт збирається заново.

### 3.2. Валідація звіту

До будь-якого планування інсталятор зобов'язаний:

- розібрати JSON без виконання вмісту та перевірити його проти офіційної схеми;
- перевірити <code>schema_version</code> і відмовитися від непідтримуваної major-версії;
- перевірити обов'язкові поля, формати часу, типи, enum-значення та внутрішні посилання на докази;
- зберегти зв'язок кожного висновку з <code>report_id</code>, джерелом і часом спостереження;
- відхилити пошкоджений, неоднозначний або внутрішньо суперечливий звіт із конкретним повідомленням.

Відсутність звіту, помилка його читання, невідповідна схема або непідтримувана major-версія означають **STOP: план не створюється**. Непідтримувані поля не можна мовчки трактувати як відомі можливості. Політика сумісності optional-полів визначається версією схеми #5, а не евристиками frontend.

### 3.3. Оцінка передумов

Readiness оцінюється не для «всього Linux на цьому ПК», а для чітко обраного сценарію: конкретного backend-а, профілю, способу отримання пакетів і цільового режиму завантаження.

Інсталятор перевіряє щонайменше:

- наявність і однозначну ідентифікацію цільового накопичувача, який користувач може вибрати;
- відомий поточний boot mode та сумісність обраної конфігурації завантаження з ним;
- наявність робочого шляху взаємодії з live-сесією (дисплей/консоль та пристрій введення), потрібного для перегляду й підтвердження;
- доступність джерел пакетів для обраного способу встановлення: перевірене мережеве підключення **або** повний локальний/offline набір;
- наявність даних, необхідних саме обраному backend adapter-у для побудови конфігурації.

Не кожне поле з <code>criticality</code> є безумовним стоп-сигналом для будь-якого сценарію. Наприклад, <code>network-installation</code> є обов'язковою передумовою, коли план має отримувати пакети з мережі; для повного локального носія мережа може не знадобитися. Аудіо, Bluetooth, webcam, suspend/resume чи прискорення графіки можуть бути важливими для подальшої повсякденної роботи, але самі по собі не повинні забороняти створення плану інсталяції, якщо вони не є вимогою обраного сценарію.

**Критична невідомість є нерозв'язаною**, коли одночасно виконуються три умови:

1. невідомий факт потрібен для безпечного встановлення або першого запуску обраної конфігурації;
2. у звіті немає достатнього прямого доказу або підтвердженої альтернативи;
3. користувач не може безпечно обійти цю залежність у межах обраного сценарію.

Нерозв'язана критична невідомість означає **STOP до показу плану запису**. Якщо існує перевірена альтернатива (наприклад, Ethernet замість неперевіреного Wi-Fi або локальний пакетний носій замість мережі), frontend показує її, джерело доказу та наслідки; користувач повинен явно обрати цю альтернативу до генерації плану.

Невідомість щодо необов'язкового пристрою, відсутність запису в зовнішній базі або неперевірена функція, яка не є передумовою обраного сценарію, дає **READY WITH WARNINGS**, а не «несумісний». Відсутність зовнішнього звіту ніколи не є доказом несумісності.

## 4. Семантика доказів у UI та рішенні

Frontend зобов'язаний зберігати такі відмінності:

| Факт у звіті | Дозволений висновок | Заборонений висновок |
| --- | --- | --- |
| <code>discovery_status=discovered</code> | Пристрій виявлений у цьому live-середовищі | Пристрій повністю працює |
| <code>driver.status=bound</code> | Драйвер прив'язаний до пристрою зараз | Усі функції пристрою протестовані |
| <code>driver.status=available-only</code> | Є відомий кандидат драйвера/модуля | Модуль завантажений або прив'язаний |
| <code>firmware.runtime_status=loaded</code> | Зафіксовано завантаження runtime firmware | Firmware пристрою оновлено до останньої версії |
| <code>functional_tests[*].status=passed</code> | Конкретний тест пройшов із зазначеним методом і часом | Усі інші функції пристрою працюють |
| <code>unknown</code> / <code>not-run</code> | Немає достатнього доказу | Пристрій несправний або несумісний |

Для кожного критичного пристрою UI показує категорію, спостережену ідентичність, статус виявлення, драйвер, runtime firmware, виконані функціональні тести, час, джерело та рівень доказу. Невідомі/неперевірені значення відображаються явно.

Не можна приховувати розбіжності між зовнішньою базою та поточним live-спостереженням. Зовнішні результати мають позначатися як зовнішні, із точністю зіставлення моделі, ревізії, ядра та дати. Вони не замінюють локальну перевірку.

**Заборонено** обчислювати один загальний бал, який приховує критичну відмову або перетворює невідоме на позитивну сумісність. Похідна рекомендація повинна містити причину, посилання на відповідні докази та впевненість.

### Поточна межа collector v0.1.0

Станом на proposal PR #9 перша реалізація <code>wsm-hwcheck</code> читає sysfs/procfs та інвентаризує CPU/DMI, PCI/USB, block storage, драйверні symlink-и та DRM connectors/modes. Вона **не доводить** end-to-end роботу мережі, Wi-Fi association, графічного прискорення, аудіо, Bluetooth, камери, suspend/resume або успішне завантаження runtime firmware. Ці факти лишаються <code>unknown</code> / <code>not-tested</code>, доки окремий перевірений збирач або тест не надасть доказ.

Виявлений storage device ще не дорівнює перевіреному доступному target для запису; прив'язаний GPU-драйвер ще не доводить коректний desktop mode. UI має показувати саме те, що реально надано звітом. Цей контракт не розширює схему чи функціональність collector.

## 5. План встановлення

План генерується тільки після успішної валідації звіту та оцінки передумов. Він є **описом наміру**, а не командою, що вже почала змінювати систему.

Мінімальна логічна структура плану:

| Поле | Вимога |
| --- | --- |
| <code>plan_version</code> | Незалежна версія контракту install plan |
| <code>plan_id</code> | Випадковий локальний ідентифікатор цього плану |
| <code>created_at</code> | Час створення |
| <code>report_id</code> + <code>schema_version</code> | Зв'язок з точним hardware report |
| <code>backend</code> | Рівно одне значення: <code>guix-system</code> або <code>nixos</code> |
| <code>backend_inputs</code> | Точні ревізії/джерела backend-а, потрібні для відтворення |
| <code>profile</code> | Явно обраний WSM software policy profile |
| <code>boot_mode</code> | Цільовий режим завантаження, узгоджений із live evidence |
| <code>storage_target</code> | Однозначно вибраний користувачем пристрій та його спостережені характеристики |
| <code>storage_operations</code> | Типізований перелік запланованих змін, файлових систем і mount points |
| <code>network_mode</code> | <code>online</code> або <code>offline</code>, із джерелом пакетів |
| <code>limitations</code> | Невідомі/неперевірені функції та свідомо прийняті обмеження |
| <code>backend_payload</code> | Декларативний backend-specific payload; не довільний shell-код |
| <code>confirmation</code> | До підтвердження відсутнє; після нього — digest точних байтів плану та факт явної згоди |

Назви наведені як концептуальні поля контракту, а не як твердження про вже існуючу JSON Schema. Остаточна machine-readable plan schema має бути окремо версіонована до того, як її почне генерувати реалізація.

План повинен бути детермінованим для однакових входів та однакового набору явних рішень користувача, крім випадкових і часових метаданих. Після показу користувачеві він не редагується «на місці»: будь-яка зміна backend-а, профілю, цільового диска, partition operation, mount mapping, boot mode чи пакетного джерела створює новий план і нове підтвердження.

Перед показом плану UI показує людське резюме:

- який backend і профіль будуть встановлені;
- який саме диск/пристрій обрано та які операції є руйнівними;
- яку файлову систему, mount mapping та boot mode буде використано;
- хто володіє bootloader та системною конфігурацією;
- які пакети/канали або pinned inputs будуть потрібні;
- які обмеження залишаться після першого запуску;
- які факти перевірені, а які тільки виявлені, невідомі чи не тестувалися.

## 6. Підтвердження та захист від застарілого плану

Перед першою операцією, що змінює диск або EFI/boot state, користувач повинен явно підтвердити **саме показаний план**. Підтвердження має бути пов'язане з SHA-256 точних байтів плану, цільовим пристроєм і переліком руйнівних операцій.

Порядок виконання:

1. Зберегти незмінні байти плану локально.
2. Обчислити digest і показати його разом із target device та операціями.
3. Отримати явне підтвердження користувача; мовчазна згода, вибір backend-а чи відкриття екрана не є підтвердженням.
4. Безпосередньо перед виконанням повторно перевірити hardware report freshness, доступність target device, його ідентичність/ємність та поточну топологію.
5. Переконатися, що digest плану не змінився і що backend досі один.
6. Лише тоді передати план єдиному backend adapter-у.

Якщо диск зник, змінився, переідентифікувався, змінилася boot mode, hardware report застарів або байти плану відрізняються — підтвердження анулюється. Потрібен новий звіт або план та нове явне підтвердження.

Не зберігати digest як заміну самому плану: виконанню підлягають лише точні перевірені байти, на які посилається підтвердження. Plan і report — локальні тимчасові дані; вони не публікуються в GitHub і не передаються зовнішнім сервісам автоматично.

## 7. Власність backend-а та заборона змішування

У межах одного плану рівно один backend:

| <code>backend</code> | Єдиний deployment path | Заборонено в тому самому плані |
| --- | --- | --- |
| <code>guix-system</code> | Нативна конфігурація Guix System та <code>guix system init</code> після перевірки | <code>nixos-install</code>, NixOS activation, паралельний generic bootloader installer |
| <code>nixos</code> | Нативна конфігурація NixOS та <code>nixos-install</code> після перевірки | <code>guix system init</code>, Guix System activation, паралельний generic bootloader installer |

Backend-specific adapter має відмовитися від плану, якщо в ньому є payload іншого backend-а, невідомий критичний ключ або непідтримувана операція. Непідтримувані поля не ігноруються мовчки.

План може описувати partition operations та mount mapping, але ownership має бути явним. Інструмент, що створює partitions/filesystems, не повинен паралельно з backend-ом встановлювати bootloader. Для Guix System цільова декларація Guix володіє описом файлових систем, облікових записів, служб і bootloader; штатний generic bootloader job frontend вимкнений. NixOS deployment використовує лише власну нативну конфігурацію та свій інсталяційний механізм.

Жоден backend не отримує дозвіл на запис лише тому, що план успішно згенерований. Перевірка конфігурації/build може бути окремим безпечним кроком, але deployment починається тільки після підтвердження.

## 8. Dry-run та інваріанти безпеки

<code>--dry-run</code> означає: **показати перевірені вхідні дані, readiness assessment і чернетку плану, після чого завершитися до будь-якого запису**.

У dry-run заборонені:

- створення/видалення/форматування partition-ів або файлових систем;
- відкриття target block device для запису;
- запис у файлову систему цільового диска;
- зміни EFI variables, boot entries або bootloader;
- запуск <code>guix system init</code>, <code>nixos-install</code> чи іншої deployment-команди;
- встановлення пакетів, завантаження модулів, firmware update або довільні системні зміни;
- мережеве надсилання hardware probe.

Read-only інвентаризація та читання sysfs/procfs дозволені. Просте створення локального JSON-файлу плану дозволяється лише у явно вказаному користувачем output path, який не є цільовим диском.

Для першого прототипу може бути використаний CLI-подібний інтерфейс:

~~~text
wsm-install --preflight --report ./hardware-report.json --backend guix-system --dry-run --plan-out ./install-plan.json
~~~

Це **приклад запропонованого інтерфейсу**, а не заява, що така команда вже реалізована. Dry-run повинен мати тести, які доводять відсутність write-capable відкриттів target device та відсутність deployment-процесу.

## 9. Мережа, приватність та offline path

Версія Hardware Evidence Report v1 у поточній пропозиції є strict-local: мережеві запити та uploads відсутні. Інсталятор має зберігати цю властивість наскрізно.

- Жодних probe uploads, зовнішніх lookups або телеметрії за замовчуванням.
- Якщо в майбутньому з'явиться зовнішній lookup чи export, це окрема дія з описом категорій даних та окремою явною згодою. Вона не повинна непомітно змінювати локальний звіт.
- Серійні номери, MAC, UUID, hostname, username, IP та storage WWN не потрібні для стандартного install plan; їх не слід збирати чи журналювати.
- Недоступність мережі або зовнішньої бази не трактується як несумісність. Вирішальним є наявність пакетів для обраного online/offline сценарію.
- Nonfree firmware, канали, binary caches та signing keys не додаються автоматично. Вибір WSM Compatibility і кожен такий компонент мають бути окремо пояснені та погоджені.

## 10. Відмови та поведінка за замовчуванням

У всіх неоднозначних ситуаціях default — **не виконувати запис**.

| Ситуація | Очікувана поведінка |
| --- | --- |
| Звіт відсутній, пошкоджений або не проходить схему | STOP; жодного install plan |
| Непідтримувана major-версія схеми | STOP; пояснити, яку версію підтримує frontend |
| Немає однозначного install target | STOP; жодного плану запису |
| Boot mode невідомий і немає перевіреного альтернативного шляху | STOP |
| Немає доступного шляху взаємодії для перегляду/підтвердження | STOP |
| Мережа не працює, але є перевірений повний offline source | Продовжити з offline plan та поясненням |
| Мережа потрібна обраному сценарію, але її працездатність невідома/відсутня | STOP або запропонувати offline alternative |
| Драйвер прив'язаний, але функція не тестувалася | Показати <code>driver-bound</code> + <code>not-tested</code>; не підвищувати статус |
| Firmware або необов'язкова функція невідома | Показати warning; не вигадувати ні PASS, ні FAIL |
| Обрано обидва backend-и або payload має змішані команди | STOP |
| Digest плану/target topology змінилися після підтвердження | Скасувати підтвердження; створити новий план |
| Deployment завершився помилкою | Зберегти безпечний журнал без секретів; не запускати інший backend автоматично |

Користувач може прийняти попередження лише тоді, коли воно не маскує критичну невідомість і для сценарію існує безпечний шлях. Погодження з попередженням не може обходити перевірку цільового диска, підтвердження digest чи правило одного backend-а.

## 11. Приймальні твердження для тестів

Наступні твердження є обов'язковими для реалізації #13 та QEMU harness #14. Це критерії, не заява про вже виконані тести.

1. Відсутній report → команда завершується ненульовим статусом, install plan не створюється, target device не відкривається для запису.
2. Валідний synthetic report v1.0.0 → frontend показує ті самі raw facts, джерела та часові позначки без підвищення рівня доказу.
3. Пошкоджений JSON, відсутні required fields або порушена схема → fail-closed до планування.
4. Непідтримувана major schema version → явне повідомлення; жодної евристичної міграції.
5. <code>driver.status=bound</code> разом із <code>functional_tests.status=not-run</code> → UI показує прив'язаний драйвер та неперевірену функцію окремо.
6. <code>firmware.runtime_status=unknown</code> не перетворюється на <code>loaded</code> або <code>missing</code> без окремого доказу.
7. Зовнішній запис/відсутність у database source не змінює локальний факт на PASS/FAIL і не блокує offline шлях сама по собі.
8. Критична невідомість без альтернативи → жодного disk plan; перевірена альтернатива створює план тільки після її явного вибору.
9. Offline scenario із повним локальним package source не потребує мережевого доступу; online scenario без перевіреного джерела зупиняється.
10. План із двома backend-ами, змішаним store або двома bootloader owners відхиляється.
11. Зміна будь-якого байта плану, target device або boot topology після підтвердження анулює confirmation.
12. Dry-run не запускає deployment, не форматує, не монтує для запису, не відкриває target block device для запису та не змінює EFI/boot state.
13. За замовчуванням немає network requests, probe uploads, firmware update або package installation.
14. Журнали та локальні plan artifacts не містять серійних номерів, MAC, UUID, hostname, username, IP чи секретів.
15. Інтеграційний тест використовує лише disposable QEMU disk; жоден шлях до фізичного диска хоста не може бути переданий VM.

## 12. Версіонування та відкриті питання

Версія цього handoff-контракту незалежна від <code>schema_version</code> hardware report і <code>plan_version</code> install plan. Зміна послідовності безпеки, значення підтвердження, ownership backend-а або умов STOP є breaking change і потребує major bump. Додавання необов'язкового поля без зміни поведінки може бути minor; редакційне уточнення без зміни контракту — patch.

До реалізації залишаються окремі рішення:

- machine-readable JSON Schema для install plan;
- перелік мінімальних функцій, що є обов'язковими саме для першого boot кожного backend-а;
- точний спосіб безпечного повторного сканування target topology перед записом;
- протокол передачі плану backend adapter-у та повернення структурованого результату;
- точне місце partition/filesystem operations у кожному backend workflow.

Ці питання не дають права послаблювати наведені інваріанти. Якщо реалізація виявить, що потрібен новий факт від collector або поле report schema, це окрема зміна у власній задачі #5/#6 після координації; frontend не повинен локально винаходити відсутній факт.
