## 1. Що означає «екосистема» в нашому контексті

Екосистема — це коли користувач не думає про межі між компонентами. Для нас це означає п'ять речей:

1. **Один вертикальний стек.** Залізо → прошивка → ядро → бекенд (Guix) → інсталятор → десктоп → документація. Кожен шар має бути узгоджений із сусідами, а не жити окремо.
2. **Один авторитетний бекенд на систему.** Уже зафіксовано в [ADR 0004](decisions/0004-nix-guix-backend-strategy.md) — тримаємо жорстко. Екосистема не допускає «двох правд».
3. **Один семантичний шлях користувача.** Від «вставив флешку» до першого робочого столу — спільні фази, типізований handoff і однакова семантика помилок. CLI/TUI/GUI можуть бути різними поверхнями взаємодії, але не окремими шляхами розгортання чи приводом дублювати backend logic.
4. **Reference hardware.** Мета — сформувати скінченний перелік reference-конфігурацій із перевіреними можливостями та чіткими межами. Конфігурація може називатися `supported` лише після успішної інсталяції, першого boot і визначених функціональних перевірок на реальному обладнанні. До цього вона має чесний статус на кшталт `candidate`, `not-tested` або `limited`, а не обіцянку підтримки. Станом на цю редакцію валідних hardware evidence profiles ще немає.
5. **Довіра як фіча.** Безпека, прозорість, `fail safely`, відсутність прихованих каналів — це не галочки, а частина продукту, яку користувач відчуває.

## 2. Принципи для агентів

### 2.1. Думай стеком, а не файлом

Перш ніж писати код, агент має відповісти: **який шар я змінюю і як це відчує користувач на сусідніх шарах**. Зміна в інсталяторі → вплив на перший boot. Зміна в профілі Guix → вплив на оновлення. Зміна в документації → вплив на довіру.

### 2.2. Кожна фіча має мати «шлях користувача»

Фіча без описаного user journey — це не фіча, а робота. Мінімум: **хто**, **коли**, **що бачить**, **що відбувається при збої**. Якщо агент не може описати це одним абзацом — фіча не готова до реалізації.

### 2.3. Evidence per claim

Якщо агент додає в README, docs або UI слово «підтримується» / «працює» / «сумісно» — поруч має бути **посилання на evidence** (лог, тест, запис у compatibility matrix). Без evidence твердження не можна позначати `supported` або `verified`. Для апаратних функцій `not-tested` та `unknown` залишаються окремими станами; `planned` означає лише те, що реалізацію ще не виконано. Не згортуйте невідоме або неперевірене в один статус.

Апаратний inventory-звіт має формат [docs/hardware/REPORT-FORMAT.md](hardware/REPORT-FORMAT.md); сам цей звіт **не є сертифікацією сумісності**. Compatibility claims тлумачаться за [docs/HARDWARE-COMPATIBILITY-VERDICTS.md](HARDWARE-COMPATIBILITY-VERDICTS.md). Для інших claims агент посилається на конкретний тест, CI run або лог із середовищем і методом перевірки. Рівні доказу (static test, Guix evaluation/build, QEMU boot, фізичне залізо) не змішуються — деталі в [CONTRIBUTING.md](../CONTRIBUTING.md).

### 2.4. `fail safely` — це поведінка, а не гасло

Кожен агент, який торкається інсталятора, оновлень або міграцій, зобов'язаний:

- визначити **hard-stop умови для конкретного сценарію**: неоднозначна ціль диска зупиняє будь-яку destructive phase; відсутність installation-critical display, input або storage path зупиняє локальне встановлення лише за відсутності перевіреного fallback;
- окремо визначити стани, які є попередженням або стосуються необов'язкової функції: невідомий дискретний GPU не блокує сценарій, якщо підтверджений iGPU забезпечує робочий display path; невідомий Wi-Fi не блокує offline-сценарій; відсутня firmware блокує лише ту критичну функцію, для якої її потреба доведена й немає альтернативи;
- перевіряти Secure Boot як умову завантаження та обраного сценарію, а не змінювати налаштування firmware автоматично;
- описати **що бачить користувач** при зупинці або попередженні, чому це сталося та як перейти до безпечної альтернативи;
- **не робити** «спробувати все одно». Висновок має відповідати [матриці апаратних verdict-ів](HARDWARE-COMPATIBILITY-VERDICTS.md): сценарій, критичність і fallback визначають наслідок.

Якщо агент вагається — правило просте: **краще зупинитися з поясненням, ніж тихо зіпсувати систему**.

### 2.5. Один бекенд, одна правда

Агент не має права:

- змішувати Nix і Guix в одній системі;
- дозволяти інсталятору писати щось на диск в обхід бекенду;
- додавати «тимчасовий» код, який дублює логіку бекенду.

Якщо завдання вимагає обійти це правило — **це не завдання, це баг у плані**. Межа «один власник установленої системи» зафіксована в [ADR 0004](decisions/0004-nix-guix-backend-strategy.md); статус інсталятора й модулів Calamares ведуть [ADR 0006](decisions/0006-hardware-first-installer-frontend.md), [ADR 0008](decisions/0008-calamares-backend-module.md) і [docs/INSTALLER.md](INSTALLER.md).

### 2.6. Повага до upstream

Ми — шар над Guix, Calamares, ядром, а не їхній форк. Якщо агент хоче «трохи поправити» upstream у себе — це сигнал, що виправлення має йти **вгору за течією**. Форк — це борг, який платить користувач.

Датовані upstream-огляди — **вхідні дані, не рішення**. Перед інтеграцією перевіряйте офіційний тег/commit, підпис і хеш саме тих байтів, які отримав WSM; downstream repack checksum не є upstream checksum. Придатність конкретної версії, API та Guix closure підтверджуйте окремим evidence і, коли змінюється архітектурна межа, ADR. Наприклад, новий Calamares stable — причина переоцінити baseline, але не автоматичне рішення повернути Calamares у роль обраного frontend.

Перелік upstream-ів і межі втручання — [docs/UPSTREAMS.md](UPSTREAMS.md).

### 2.7. Ліцензійна гігієна з першого рядка

Кожен агент, який додає залежність, має перевірити:

- чи дозволяє ліцензія конкретної залежності її заплановане використання й розповсюдження у відповідному профілі;
- чи збережено upstream copyright, license та notices, а також виконано вимоги щодо source offer і торговельних марок, якщо вони застосовні;
- чи не додає залежність невільний компонент непомітно та чи відповідає явному поділу WSM Free / WSM Compatibility;
- чи не змішується власна ліцензія WSM ВОЛЬНІСТЬ (`LicenseRef-Volnist`) із ліцензіями сторонніх компонентів: WSM не переліцензовує upstream-код.

[docs/LICENSING.md](LICENSING.md), [docs/ETHICS.md](ETHICS.md) і [ADR 0003 — free by default](decisions/0003-free-by-default.md) — обов'язкові до прочитання перед будь-яким PR із новою залежністю. GPL-3.0-or-later не є загальною ліцензією WSM і не має механічно нав'язуватися всім залежностям.

## 3. Пріоритети роботи агентів

### Пріоритет 1 — те, що робить екосистему когерентною

- **Інсталятор як єдиний шлях**: один канонічний user journey, одна послідовність фаз, один типізований план і один Guix backend. CLI/TUI/GUI можуть бути різними способами взаємодії лише тоді, коли використовують той самий handoff та acceptance-контракт; документація не повинна розводити користувача на різні процедури чи ручні обхідні команди.
- **Перший boot**: агент, відповідальний за перший запуск, має описати **кожен екран** і **кожну точку збою**.
- **Оновлення й відкат**: зробити видимими номер покоління, source/config identity, результат build та activation, доступні попередні покоління й межі відновлення. Відкат Guix generation повертає декларативний стан системи, але **не** відкочує автоматично `/var/lib/<service>` або `/home/<user>`; міграції й persistent data потребують окремого ідемпотентного/recovery-контракту. Не обіцяти атомарний rollback між цими областями без окремої перевірки. Канонічні межі описані в [docs/STATELESS-CONFIGURATION.md](STATELESS-CONFIGURATION.md).
- **Reference hardware matrix**: один канонічний реєстр кандидатів ведеться в межах [#8](https://github.com/juv4uk/wsm-desktop/issues/8); формування профілів і package manifests — окрема робота [#171](https://github.com/juv4uk/wsm-desktop/issues/171). Не змішуйте власників: inventory report має власний формат у [docs/hardware/REPORT-FORMAT.md](hardware/REPORT-FORMAT.md), profile evidence bundles — у [docs/HARDWARE-PROFILE-EVIDENCE.md](HARDWARE-PROFILE-EVIDENCE.md), а семантика verdict-ів — у [#22](https://github.com/juv4uk/wsm-desktop/issues/22) та [docs/HARDWARE-COMPATIBILITY-VERDICTS.md](HARDWARE-COMPATIBILITY-VERDICTS.md). Це цільовий реєстр, а не наявний список сертифікованих машин: валідних physical evidence profiles ще немає.

### Пріоритет 2 — те, що робить екосистему приємною

- **Узгодженість UX**: однакові патерни в інсталяторі, першому запуску, налаштуваннях, оновленнях. Агент, який додає новий екран, зобов'язаний перевірити його проти існуючих.
- **Onboarding**: від «вставив флешку» до «перший робочий стіл» — максимум кроків має бути **виміряний** і **зменшений**.
- **Документація як продукт**: docs — це не «потім», це частина UX. Кожен PR із поведінкою користувача тягне за собою docs.

### Пріоритет 3 — те, що робить екосистему стійкою

- **Тести на реальному залізі**: не лише QEMU. Без цього compatibility matrix — фікція.
- **Моніторинг регресій**: кожен новий реліз профілю — проти reference hardware.
- **Decision records**: кожне архітектурне рішення — короткий ADR у [docs/decisions/](decisions/). «No decision yet» — тимчасовий стан, не стиль.

## 4. Антипатерни — що агентам заборонено

- **Додавати другий DE / другу оболонку** до стабілізації першої.
- **Обіцяти підтримку ARM / RISC-V / серверів** до стабільного x86_64 desktop.
- **Писати «працює» без evidence** — у README, docs, UI, commit message.
- **Робити «тимчасові» обхідні шляхи** навколо бекенду — вони стають постійними.
- **Форкати Calamares / Guix / ядро** замість upstream-патчу.
- **Додавати невільні компоненти тихо** — лише через явний, задокументований канал.
- **Цитувати зовнішні огляди (включно з AI) як «рев'ю»** — це вхідні дані, не рішення. Рішення — в ADR.
- **Лишати збій конвеєра без причини в місці, яке можна прочитати.** Логи задачі GitHub потребують авторизації, тому агент без неї бачить лише «Process completed with exit code 2». Кожен такий збій коштує повного прогону вгадування. Причина мусить писатися туди, що читається без авторизації — коментар до коміту з хвостом логів; зразок у [`.github/workflows/release-minimal-live.yml`](../.github/workflows/release-minimal-live.yml), крок «Повідомити причину збою».
- **Публікувати повносистемну гарантію сумісності до першої успішної інсталяції, першого boot і функціональних acceptance-перевірок на реальному обладнанні** — неприпустимо. Read-only hardware inventory та окремі обмежені спостереження можна публікувати раніше лише з явним статусом і без заяви `supported`.

## 5. Definition of Done для фічі в екосистемі

Механіку перевірок (команди, exact-head CI, merge policy) визначає [CONTRIBUTING.md](../CONTRIBUTING.md). Цей розділ задає **критерії когерентності**, без яких фіча не вважається готовою, навіть якщо всі тести зелені.

Фіча вважається готовою, лише якщо виконано **все**:

1. **User journey описано** — хто, коли, що бачить, що при збої.
2. **Вплив на сусідні шари перевірено** — інсталятор, перший boot, оновлення, docs.
3. `fail safely` **поведінка визначена** — тригери зупинки й повідомлення.
4. **Evidence додано для конкретного claim** — тест, лог або профіль з точним source SHA, конфігурацією/inputs, середовищем, командою, результатом/exit code та digest артефакту, якщо він створювався. Формат має відповідати класу доказу; hardware inventory не замінює build, QEMU, installer чи physical acceptance evidence.
5. **Docs оновлено** — не «потім», а в тому ж PR.
6. **Ліцензійна перевірка пройдена** — сумісність, nonfree, policy.
7. **ADR оновлено**, якщо рішення архітектурне.
8. **Жодних «тимчасових» обходів** бекенду чи upstream.

Якщо хоч один пункт відсутній — фіча **не готова**, навіть якщо код працює.

## 6. Як агентам комунікувати між собою

- **Одне нормативне джерело рішення** — відповідний ADR або policy у [docs/decisions/](decisions/) із записом у [docs/DECISIONS.md](DECISIONS.md). Канонічний issue є місцем координації та фіксації пропозицій, як вимагає реєстр; його коментарі й PR review допомагають обговоренню, але не замінюють затверджений документ. Чати — лише для синхронізації.
- **Один канонічний формат апаратного inventory** — [docs/hardware/REPORT-FORMAT.md](hardware/REPORT-FORMAT.md); compatibility verdict — за [docs/HARDWARE-COMPATIBILITY-VERDICTS.md](HARDWARE-COMPATIBILITY-VERDICTS.md). Для інших типів claims — конкретний тест/CI/log із provenance, а не непідтверджене «у мене працює».
- **Один формат задач** — кожна задача має містити: шар, user journey, `fail safely` тригери, evidence-план, вплив на docs.
- **Ескалація замість обходу**: якщо агент не може виконати задачу без порушення принципів — він **зупиняється й ескалує**, а не робить «як тимчасово».

## 7. Одне речення для кожного агента

**Ми будуємо не набір компонентів, а один досвід — і кожен шар має робити сусідні шари кращими, а не компенсувати їхні недоліки.**

Якщо агент пам'ятає лише це — решта рекомендацій випливає з нього.
