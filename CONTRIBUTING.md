# Внесок у WSM Desktop

<!-- SPDX-License-Identifier: LicenseRef-Volnist -->

Дякуємо за інтерес до WSM Desktop. Проєкт перебуває на ранній стадії; найцінніший внесок зараз — перевірювані технічні дослідження, невеликі зміни та точна документація.

## Перед початком

1. Прочитайте README та відповідні документи з каталогу docs.
2. Перевірте, чи не існує вже issue або pull request на ту саму тему.
3. Для зміни архітектури спочатку запропонуйте короткий ADR у docs/decisions.
4. Не додавайте бінарні прошивки, драйвери, образи або інші сторонні файли без перевірки походження, ліцензії та права на розповсюдження.

## Правила змін

- Зберігайте зміни вузькими та придатними до перевірки.
- Не видавайте неперевірену конфігурацію за працездатну.
- Не запускайте інсталяційні команди на реальних дисках під час розробки.
- Не додавайте сторонні канали, підписні ключі чи сервери підстановок без окремого обґрунтування.
- Для стороннього коду зберігайте upstream copyright та license notices.
- Код і конфігурація мають містити SPDX-License-Identifier там, де це доречно.
- Документація проєкту спершу ведеться українською; переклади не повинні суперечити українському першоджерелу.

## Перевірки

Перед pull request виконайте:

    make check

Коли змінюється systems/minimal.scm і доступний Guix:

    make check-system

Не запускайте guix system init на фізичному диску для перевірки. Інтеграційні випробування виконуються на одноразовому образі віртуальної машини.


## Якість тестів і робота з агентами

Тести мають захищати поведінку, а не підтверджувати, що агент записав очікуваний рядок. Перед додаванням тесту сформулюйте конкретну регресію, яку він ловитиме.

- Новий тест має бути **червоним без виправлення і зеленим із ним**. Перевіряйте реальну функцію, CLI, контракт або межу безпеки, а не лише grep по файлу чи значення, яке тест сам щойно створив.
- Не додавайте тести на точний вміст великих згенерованих файлів, загальну кількість записів або декларативний рядок конфігурації. Для Scheme перевіряйте обчислення через Guix; для конфігурацій тестуйте реальну інваріанту, яку вони мають забезпечувати.
- Не тестуйте поведінку власного stub замість реального компонента. Якщо справжнє середовище недоступне, чітко позначайте структурну перевірку як обмежений доказ.
- Розширюйте наявний тестовий файл відповідної підсистеми. Окремий test-файл виправданий лише для нового незалежного контракту або окремого runner-а.
- Спочатку запускайте найвужчі релевантні тести, потім один раз повний `make check` перед завершенням зміни. Не перезапускайте suite лише заради іншого виводу або в надії, що випадкова помилка зникне.
- Зберігайте повний вивід перевірки в лог; не пропускайте тестовий процес через `grep`, `head` або `tail`, якщо це може приховати причину збою.
- Якщо падає тест у незміненій підсистемі, один раз перевірте його на базовому коміті. Якщо він там також падає, зафіксуйте попередній дефект окремо, не маскуйте його в поточному PR.

### Агентська координація та злиття

- Перед роботою перевірте чинні issue, відкриті PR і останній `main`; не створюйте паралельну реалізацію вже наявного рішення.
- Один PR має одну логічну мету. Не редагуйте один і той самий файл паралельно в кількох гілках без явного узгодження; фіксуйте власника ділянки роботи й інтегруйте завершені зміни послідовно.
- Перед review синхронізуйте гілку з актуальним `main`. Після нових комітів повторно перевіряйте саме поточний HEAD, а не попередній зелений SHA.
- `queued`, `pending`, `cancelled`, відсутній або застарілий CI не є успішною перевіркою. Зливайте лише після завершення обов'язкових перевірок exact HEAD, без конфліктів і з перевіреним diff.
- У підсумку зазначайте точний коміт, команди, результати та межі. Не називайте синтетичний fixture апаратним доказом і не приписуйте фізичному обладнанню результати QEMU.

### Рівні доказу та безпека

- Розрізняйте статичні/unit checks, Guix evaluation/build, QEMU з TCG, QEMU з KVM та фізичне обладнання. Кожен рівень доводить лише те, що реально було виконано на ньому.
- Для інтеграційних інсталяційних тестів використовуйте одноразові `qcow2`-диски. Перед запуском перевіряйте, що VM не під'єднана до дисків хоста; не експериментуйте на дисках із цінними даними.
- До появи окремо reviewed та авторизованого APPLY-шляху інсталятор лише формує план. Не запускайте `mkfs`, `mount`, `guix system init` або інші операції зміни диска на машині розробника.
- Upstream-джерела фіксуйте незмінними ревізіями та checksum/signature evidence. Не імпортуйте чужі build-рецепти без review і не виконуйте завантажені upstream-скрипти лише тому, що їх знайшов updater.
- Якщо в майбутньому додаються оновлення або міграції стану, вони мають мати явного власника, бути ідемпотентними, розділяти user/system scope та мати визначену поведінку при частковому збої. Не запускайте непомітні фонові міграції, які можуть обійти видиме підтвердження користувача.

## Pull request

Опишіть:

- проблему або потребу;
- чому запропоноване рішення відповідає архітектурі;
- змінені компоненти;
- виконані перевірки та їхній результат;
- обмеження, які залишаються.

Не включайте секрети, приватні ключі, паролі або персональні дані в коміти та журнали.

## Мовна політика документації

Раніше правило не було зафіксоване: README був англійською, а CONTRIBUTING.md і SECURITY.md — українською, і ніде не було сказано, яка копія є оригіналом. Тепер правило явне і його перевіряє `scripts/check_docs.py`.

- **Канонічна мова всієї документації — українська.** `README.md`, `CONTRIBUTING.md`, `SECURITY.md` і всі документи в `docs/` ведуться українською.
- **Англійські переклади лежать поруч і мають суфікс `.en.md`**: `README.en.md`, `CONTRIBUTING.en.md`, `docs/ETHICS.en.md`. Переклад ніколи не буває єдиною копією документа і має посилатися на канонічний файл.
- Переклади опційні й можуть відставати. У разі розбіжності істинним є канонічний документ.
- Код, повідомлення комітів і обговорення в issue можуть бути англійською, коли це полегшує роботу з upstream.

Якщо документ справді належить іншою мовою, переносьте весь документ, а не тримайте другу копію під іншою назвою.
