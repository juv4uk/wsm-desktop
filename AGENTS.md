# Інструкції для агентів WSM Desktop

Цей файл — точка входу для автоматизованих агентів і людей, які виконують багатокрокову роботу в репозиторії. Він доповнює, а не замінює [CONTRIBUTING.md](CONTRIBUTING.md), ADR, issue acceptance та версійні контракти.

## Де шукати правила

- [CONTRIBUTING.md](CONTRIBUTING.md) — загальні правила внеску, ліцензії, перевірки й мовна політика.
- [agents/skills/](agents/skills/) — покрокові процедури для конкретних типів задач. Перед зміною інсталятора прочитайте [installer-lifecycle.md](agents/skills/installer-lifecycle.md).
- [docs/](docs/) — архітектура, рішення, acceptance та довідкова документація.
- [schemas/](schemas/) і відповідні модулі — машинно-читані контракти. Не змінюйте версійний контракт мовчки.
- README — вступ для користувачів і розробників; не використовуйте його як другий реєстр архітектурних рішень.

Не створюйте другу копію списку команд, схем, профілів або статусів, якщо вже є один канонічний файл/validator. Інші документи мають посилатися на власника цього контракту.

## Перед початком роботи

1. Прочитайте цей файл, CONTRIBUTING.md та безпосередньо пов'язані ADR/документи.
2. Перевірте точний HEAD `main`, робочий стан, пов'язаний issue, відкриті PR та гілки. З'ясуйте, чи вже існують CLAIM, активний власник або реалізація тієї самої зміни.
3. Один workstream має одного відповідального власника, одну узгоджену гілку й один canonical PR. Не відкривайте конкурентний PR на ті самі файли/acceptance. Якщо робота вже належить іншому агенту, додайте review/координаційний коментар або погодьте передачу; не переписуйте чужу гілку мовчки.
4. Відокремлюйте обов'язковий deliverable від додаткових досліджень. Не розширюйте scope лише тому, що знайшли цікаву технологію або сторонній дефект.
5. Спершу шукайте придатні напрацювання в `sens`, `wsm-lazarus`, `wsm-my-lisp`, `cml` та інших власних репозиторіях. Переносьте код/метод лише після перевірки меж семантики, контракту, ліцензії та тестів; не копіюйте висновки без їхніх доказів.

## Правила доказів

- Кожен технічний висновок має точне джерело: commit/blob SHA, команда, версія інструмента, середовище, exit code і результат.
- Розрізняйте `pass`, `fail`, `not-run`, `unknown`, `not-assessed`, `incomplete` та `not-measured`. Наявність package definition, драйвера, профілю чи тестового fixture не доводить збірку, runtime або фізичну працездатність.
- CI `queued` або `pending` — не успіх. Перевіряйте runs саме для поточного PR HEAD SHA. Для нових тестів дивіться журнали й переконайтеся, що вони реально були виявлені та виконані; зелений загальний job без нового тестового класу не є доказом цього тесту.
- Не маскуйте невдалу команду через `|| echo`, `tail -1`, фільтрацію помилок чи перетворення `incomplete` на shell-success. Невдалий acceptance має дати ненульовий вихід і зберегти діагностику.
- Performance/energy claims потребують однакової функціональної роботи, точного provenance, повторів та відповідного датчика. Час не є джоулем; parity не є performance evidence.

## Перевірки та злиття

Перед PR виконайте `make check` та вузькі тести для змінених компонентів. Інтеграційні системні зміни перевіряйте в disposable QEMU/VM; не використовуйте фізичні диски, EFI хоста, Ventoy або firmware для автоматичних тестів.

Зливати PR можна лише коли одночасно виконано все:
- PR не є Draft, scope та diff перевірені;
- base синхронізований з актуальним `main`, немає нерозв'язаних конфліктів і дубльованої роботи;
- усі обов'язкові checks успішні саме на поточному head SHA; `skipped`, `cancelled`, `queued` і старий green run не рахуються як успіх;
- перевірені acceptance та безпекові межі, а залишкові обмеження чесно записані;
- злиття виконується із передачею `expected_head_sha`, після чого перевіряються merge commit і новий `main`.

Не зливайте PR лише через `mergeable=true`, малий diff, авторський локальний тест або бажання прибрати чергу. Закривайте superseded PR тільки після перевірки, що корисні зміни перенесені в canonical PR.

## Мова та документація

Українська — канонічна мова документації й інженерних рішень WSM. Англійський переклад, якщо він потрібен, зберігайте поруч із суфіксом `.en.md` та не дозволяйте йому суперечити українському оригіналу. Деталі внутрішніх процедур агентів зберігайте в `agents/skills/`, архітектурні рішення — у `docs/`, а не в користувацькому README.

## Межі безпеки

Не запускайте APPLY, форматування, repartition, `guix system init` чи інші операції запису на фізичному диску під час розробки. Не додавайте відомі паролі, секрети або приватні ключі в образи, source чи журнали. Не змінюйте BIOS/UEFI/firmware, governor, power limits чи апаратний стан без окремої явної процедури й дозволу. Preflight і звичайний hardware report мають залишатися read-only.
